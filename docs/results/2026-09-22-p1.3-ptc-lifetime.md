# P1.3 PTC lifetime: thread-exit drain fixed; resize items still open

**Date:** 2026-09-22
**Commits:** `d182f71` (regression), `a936c9b` (fix), `b332f53` (control arm)
**Hardware:** `c7i.2xlarge` (x86_64), `c7g.2xlarge` (aarch64)
**Method:** isolated builds via `scripts/ec2/verify-isolated.sh`

Two agents assigned to this item died on timeouts without producing code, so
the drain defect was fixed directly. **Only P1.3a is fixed.** The two resize
defects (P1.3b, P1.3c) are analyzed but not fixed, and are listed as open
below.

## P1.3a — thread exit lost half of every cached bin (FIXED)

`umem_ptc_destroy()` called `umem_ptc_bin_flush()`, which deliberately flushes
only half a bin, exactly once per bin, and then freed the PTC. Every object
still in a bin at that point lost its only reference while the slab layer went
on counting it as allocated. Its comment claimed "Flush all bins", which the
code did not do.

The yield accounting was also wrong: it added `bin->count` *after* the flush,
so it counted the remainder rather than the number flushed.

### Fix

`umem_ptc_bin_flush()` keeps the steady-state half-flush, so an overflowing
bin still retains objects for reuse. A new `umem_ptc_bin_flush_all()` drains
completely and is used only at thread exit, with an assertion that the bin is
empty afterwards.

Separately, `umem_ptc_get()` ignored `pthread_setspecific()` failure, leaving a
thread with a PTC but no destructor — its cached objects could never be
returned. It now declines to use a PTC on that thread and falls back to the
magazine layer: slower, but loses nothing.

### How this was measured, and one wrong turn

The first version of the regression thresholded *absolute* growth in
outstanding buffers. That cannot distinguish "retained by the magazine, depot,
and slab layers" from "lost". On the fixed build the same workload grew the
count from ~315 to ~1092 over six rounds with the PTC **completely disabled**,
where no PTC loss is possible — so that threshold would have failed even a
PTC-free allocator, and passing it would have proved nothing.

The regression now runs both arms in one process — PTC active, then
`umem_ptc_enabled = 0` — and requires the PTC arm's growth not to exceed the
control by more than a margin. The control subtracts out ordinary retention.

Validated by temporarily reverting the fix, so the test is known to
discriminate rather than merely pass:

| Build | PTC arm growth | PTC-off control | Margin | Verdict |
|---|---:|---:|---:|---|
| pre-fix (`umem_ptc.c` reverted) | **896** | 71 | 192 | FAIL |
| post-fix, x86_64 | 189 | 82 | 192 | PASS |
| post-fix, aarch64 | 205 | 115 | 192 | PASS |

A 12x separation pre-fix. The earlier absolute-growth run also showed the raw
leak directly: 560, 994, 1458, 1916, 2266, 2698 outstanding buffers across six
rounds, about 430 per round, ~54 per exiting thread — consistent with stranding
half of each 96-object bin.

## OPEN: P1.3b — magazine capacity is not sampled with the magazine

In `_umem_alloc`'s PTC magazine path, the code obtains a magazine from
`umem_depot_alloc_trylock()` — which validates it against the *current*
magtype — and then separately reads `cp->cache_magtype->mt_magsize` to set
`mag->magsize`. `umem_cache_magazine_resize()` can change the magtype between
those two steps, so an old, smaller magazine can be indexed with the new,
larger capacity. The free side samples the new size separately from obtaining
the magazine as well.

Reachable in a default build: ordinary depot contention schedules a resize
independently of the `umem_magazine_tuning` option.

Not fixed. The fix needs the magazine and the capacity it is used with to be
one consistent decision — derive the capacity from the magazine's own source
magtype, or re-validate both under the same lock. Verifying it needs a
high-core box driving depot contention while forcing resizes, under ASan.

## OPEN: P1.3c — populated magazines are discarded on a magtype mismatch

`umem_ptc_mag_return_trylock()` and `umem_ptc_mag_return()` check
`UMEM_MAGAZINE_VALID` and, on a magtype mismatch, free just the magazine shell
via `_umem_cache_free(mag_cache, mp)` without draining the objects inside.
Callers pass a full loaded magazine (the `&cp->cache_full` call site) and a
possibly-full previous magazine down the "empty" path. Every object inside is
lost.

Not fixed. `umem_ptc_mag_flush_all()` already shows the correct draining
pattern; the fix is to drain before discarding and to make the full/empty
classification honest.

## Why the two open items were not folded in

Both are ownership races around magazine resize, and both need contention
driven on a 192-vCPU box with ASan to demonstrate a pre-fix failure rather
than argued from source. Shipping them without that evidence would repeat the
pattern this plan exists to correct. They remain Phase 1 blockers in
`docs/plans/2026-09-21-production-readiness.md`.
