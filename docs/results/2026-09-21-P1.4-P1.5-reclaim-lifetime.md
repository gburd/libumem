# P1.4 / P1.5 — cache destruction with retained slabs, and reclaim metadata
# preservation + synchronized publication

Plan: `docs/plans/2026-09-21-production-readiness.md` §P1.4, §P1.5.
Fixes: `f4383b5` (P1.4, P1.5a/b/c), `a7aa4f8` (the reap re-entry deadlock the
P1.5c regression uncovered).
Regressions: `60d8eae`, extended in `a7aa4f8` and `a1296d0`.

Every result below was produced by `scripts/ec2/verify-isolated.sh`, which
ships `git archive <sha>` rather than the working tree, so no other agent's
in-flight edits are in any of these builds. Workers: `intel-lo@reclaim`
(c7i.2xlarge, x86_64) and `arm-lo@reclaim` (c7g.2xlarge, aarch64), both
4 KiB pages, gcc 11 (AL2023).

## Root causes

### P1.4 — destroy leaked every retained empty slab

`umem_reclaim_enabled` defaults to 1, so `umem_slab_free()`'s last-object
path marks the emptied slab `SLAB_DIRTY` and leaves it linked for the update
thread instead of destroying it. `umem_cache_destroy()` removed the cache
from the update list, purged magazines, **logged** a nonzero `cache_buftotal`
("not empty"), set landmine ctor/dtor, freed the per-CPU/depot arrays and
`vmem_free`d the descriptor — it never destroyed those slabs. Their backing
spans, and for a `UMF_HASH` cache their external slab/bufctl metadata, stayed
allocated with `slab_cache` pointing at freed memory.

Two further leaks on the same path, found while fixing it:

* the rseq per-CPU loaded magazines were pushed onto the depot **after**
  `umem_cache_magazine_purge()`, so nothing reaped them — magazine and rounds
  both abandoned;
* they were labelled full/empty by `rounds > 0`, which mislabels a partially
  filled magazine.

### P1.5a/b — reclaim discarded metadata the allocator reads again

`umem_slab_reclaim()` advised the whole slab for `UMF_HASH`, and everything
below the metadata page otherwise. Two kinds of metadata live *inside* the
buffer region and are written **only** by `umem_slab_create()`, with nothing
rebuilding them when `umem_slab_alloc()` reactivates an idle slab:

* **buftags + `UMEM_FREE_PATTERN`** (`UMF_BUFTAG`). `umem_cache_alloc_debug()`
  validates `bt_bxstat == (bt_bufctl ^ UMEM_BUFTAG_FREE)` and the free
  pattern *before* the constructor runs, so a constructor cannot repair them.
* **embedded bufctls' `bc_next` links** (non-`UMF_HASH`), spread across every
  page of the buffer region.

`MADV_DONTNEED` zero-fills both.

### P1.5c — `slab_state` was published unlocked

`umem_slab_reclaim()` stored `SLAB_CLEAN` as a plain store while
`umem_cache_reclaim_pages()` had dropped `cache_lock`, on the madvise path
*and* on the nothing-to-advise path. `umem_slab_alloc()` and
`umem_slab_free()` read `slab_state` under that lock. A mutex serializes a
reader only against writers that also take it.

### P1.5c, two controls

`/race` passed pre-fix without TSAN, as an unsynchronized store may well not
produce a visible failure. Under TSAN at adequate sensitivity it does:

```

  Read  of size 4 by thread T1 (mutexes: write M1876):
    umem_slab_alloc            umem.c:1613
  Previous write of size 4 by thread T6 (mutexes: write M63):
    umem_slab_reclaim          umem.c:3968
    umem_cache_reclaim_pages   umem.c:4068
    umem_cache_update          umem.c:4258
    umem_cache_applyall        umem.c:891
    umem_update_thread         umem_update_thread.c:139
SUMMARY: ThreadSanitizer: data race umem.c:1613 in umem_slab_alloc
```

(`prefix-evidence/2026-09-21-P1.5c-tsan-prefix-intel.log`.) The reader holds
`cache_lock` (M1876), the writer holds a different mutex — the race as
described.

**Two of my own measurements were wrong first and are recorded as such**,
because each would have produced a false conclusion:

1. A TSAN baseline that reverted only the state stores but kept the *post-fix*
   madvise limit advised the embedded `umem_slab_t` for non-hash caches and
   crashed — 3 unrelated reports, `SIGABRT`, zero `slab_state` reports. It
   was measuring a failure the pre-fix code never had. Fixed by reverting the
   limit ternary too, and by making the control assert its own
   post-conditions before building.
2. A 3 s run with `reap_interval=1` reported **zero** `slab_state` races
   pre-fix. That is insensitivity, not absence: the limiter allowed roughly
   one reclaim pass per second. The baseline and the post-fix run now both
   use 30 s with `reap_interval=0`. A post-fix zero only means something
   against a pre-fix baseline taken at the same sensitivity.

## A pre-existing deadlock the P1.5c regression found

`/race` hung on x86_64 and timed out on aarch64. gdb on the stuck process:

```
umem_cache_applyall(umem_cache_update)        [holds umem_cache_lock]
  umem_cache_reclaim_pages -> umem_slab_destroy -> vmem_free
    -> _umem_cache_free -> _umem_cache_alloc     (vmem seg refill)
      -> umem_slab_create -> vmem_alloc -> vmem_xalloc
        -> vmem_reap -> umem_reap -> umem_updateall
          -> mutex_lock(&umem_cache_lock)        [same thread, blocks]
```

`umem_cache_lock` is not recursive. **Pre-existing, not fix-induced**: the
update thread makes the same `umem_cache_applyall` call
(`umem_update_thread.c:139`) and the destroy path that triggers it is
unchanged from pre-fix code. It stayed latent because `umem_reap()`'s rate
limiter normally returns before reaching `umem_updateall()`.

Fixed at the shared function: `umem_reap()` returns immediately when
`IN_UPDATE()`. Such a reap is redundant (the pass in progress is already
doing that work), and reaps have always been droppable — `umem_reap()`
already returns early when another reap is active or the interval has not
elapsed.

Control (`prefix-evidence/2026-09-21-P1.5c-reap-reentry-control.log`): with
the guard deleted and nothing else changed, `/reap_reentry` hangs (`rc=124`
at the 90 s timeout); with it, it completes in 5 s.

The tests were wrong in the same way and were corrected — an incorrect driver
is what made this look like a fix-induced hang. `/race` now drives reclaim
through `umem_reap()`, and the reuse cases publish `umem_st_update_thr`
before each pass exactly as `umem_st_update()` does, so `IN_UPDATE()` holds
during a pass as it does in the library.

## What changed

`umem.c` only.

* **`umem_cache_drain_slabs()`** (new) — walks the `cache_nullslab` list
  (which threads *all* slabs; `cache_freelist` is only where the free-buffer
  portion starts), unlinks `refcnt == 0` slabs under `cache_lock`, destroys
  them outside it. Called from `umem_cache_destroy()` after the magazine
  purge and before the descriptor is freed, since `umem_slab_destroy()` reads
  `cache_arena`, `cache_slabsize`, `cache_flags` and `cache_bufctl_cache` out
  of it. Slabs with live buffers are left alone and reported: freeing a span
  under a live buffer is worse than leaking it.
* **rseq magazines in destroy** — drained *before* the purge, each with
  `umem_magazine_destroy(mag, rc->rounds)`.
* **`umem_slab_keeps_metadata()`** (new) — excludes `UMF_BUFTAG` and
  non-`UMF_HASH` caches from page discard, documenting which metadata lives
  where and why a constructor cannot substitute for it.
* **`umem_slab_reclaim()`** — advises only; no state write.
* **`umem_cache_reclaim_pages()`** — performs `RECLAIMING -> CLEAN` after
  retaking `cache_lock`, with `ASSERT`s on the expected state. The invariant
  is stated at both the writer and the reader.
* **`umem_reap()`** — declines when `IN_UPDATE()`.

Deliberately not reclaimed (`ponytail:` in the code with the upgrade path):
page discard for multi-page non-hash slabs and for debug builds. Correctness
over reclaiming, per the plan. Default-arena non-hash slabs are one page and
never had a page to discard, so nothing regresses there; non-debug hash
caches, where the large multi-page slabs live, still reclaim. The upgrade
path is to rebuild the in-buffer metadata on reactivation and only then
discard.

## RSS / retention observation

`test/bench/probe_reclaim_rss` (**an observation, not a benchmark** — no
timing, no thread count, no allocator comparison, and nothing here supports a
throughput claim). 20 000 × 512 B on a private 64 MiB arena, 4 KiB
quantum → `UMF_HASH`, 4096 B slabs, no buftags. x86_64
(`2026-09-21-P1.4-P1.5-rss-and-tsan-intel.log`; aarch64 within 0.5 MiB
throughout):

| phase | default (delay 30) | delay 0 | reclaim off |
|---|---|---|---|
| baseline | 5052 kB / 0 B | 5052 kB / 0 B | 5092 kB / 0 B |
| after alloc | 16260 kB / 10240000 B | 16260 kB / 10240000 B | 16300 kB / 10240000 B |
| after free | 16260 kB / 10240000 B | 16260 kB / 10240000 B | 16684 kB / **0 B** |
| after 1 update pass | 16260 kB / 10240000 B | **6260 kB** / 10240000 B | 16684 kB / 0 B |
| after 8 more passes | 6644 kB / **0 B** | 6644 kB / **0 B** | 16684 kB / 0 B |
| after cache destroy | 6632 kB / 0 B | 6632 kB / 0 B | 16672 kB / 0 B |

(RSS / `vmem_size(arena, VMEM_ALLOC)`.)

Three things this shows, and nothing more:

* **Reclaim works as designed on this cache.** With `delay 0`, one update
  pass drops RSS 16260 → 6260 kB while the arena still holds all 10 MB: the
  pages were discarded, the address space retained. Eight further passes
  release the spans themselves (arena → 0).
* **`reclaim=0` returns spans immediately but keeps the RSS.** The arena hits
  0 B at the free, yet RSS stays at 16684 kB, because the freed pages return
  to `umem`'s own arenas rather than to the kernel. Reclaim is what lowers
  RSS; span accounting alone does not.
* **Destroy no longer leaks.** In every mode the arena ends at 0 B. Pre-fix
  the single-slab case ended at 4096 B (above); at this scale the update
  passes had already destroyed the slabs before destroy ran, which is exactly
  why the P1.4 regression uses the minimal one-slab sequence instead of a
  bulk workload — a bulk test would have passed while the bug was live.

No claim is made about fragmentation: the harness's fragmentation accounting
is itself under repair in P2.2, so any number from it would be untrustworthy.

## Found, not fixed

* **`test/stress/repro_interpose_fork.c` does not compile** (another agent's
  file, in `@interp`'s scope): `uintptr_t` at lines 67 and 141 without
  `#include <stdint.h>`, which fails the whole-tree `make` on both arches.
  Reported. All results above predate it or build only the needed targets.
* **`umem_reap()`'s fast-path early return reads `umem_reaping` and
  `umem_reap_next` outside `umem_update_lock`** (`umem.c:4392–4393`), which
  TSAN reports. It is a deliberate unsynchronized pre-check, re-tested under
  the lock — but it is a torn-read data race by the letter, and the same
  standard P1.5c is being held to. Left alone: it is not in P1.4/P1.5's scope
  and the fix belongs with whoever owns the reap/update state machine.
* **`vmem_hash_insert` / `vmem_hash_delete` / `vmem_hash_rescale` races**
  (`vmem.c:372, 403, 1649`), reported on both arches in every TSAN run. Not
  in scope; `vmem.c` is not in my file set.
* **`test_slab_reclaim_madvise`** (`test/unit/test_coverage.c:1585`) still
  proves nothing — it never shows advice happened nor reallocates from a
  `CLEAN` slab. Left in place; the `/reclaim` suite is what covers this now.
  It should be deleted or rewritten by whoever next touches that file.
* **`umem_cache_destroy()` still only logs** when a cache is destroyed with
  live buffers. Draining is now correct for empty slabs; deciding whether a
  destroy with outstanding allocations should abort rather than log is a
  documented-contract question (Phase 3), not a reclamation bug.
