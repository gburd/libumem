# P1.3b and P1.3c: magazine capacity/resize race and populated-magazine discard

**Date:** 2026-09-22
**Commits:** `756fe71` (fix), `c73ffbe`…`fc6f32a` (regressions and their corrections)
**Hardware:** `c7i.2xlarge` (x86_64, 8 vCPU), `c8g.metal-48xl` (aarch64, 192 vCPU)
**Method:** isolated builds via `scripts/ec2/verify-isolated.sh` (committed
content only, per-worker instances `intel-lo@ptc2` / `arm-hi@ptc2`)

Both items are now fixed with demonstrated pre-fix failures. They complete
Phase 1 as listed in `docs/plans/2026-09-21-production-readiness.md`; P1.3a was
fixed previously (`docs/results/2026-09-22-p1.3-ptc-lifetime.md`).

**The honest headline first:** both defects are real and both fixes are
verified, but the two differ enormously in how often they can be expected to
occur. P1.3c fires on the *first* magazine resize under ordinary load and
destroys a full magazine each time — measured directly. P1.3b needs a resize to
land inside a window a few tens of nanoseconds wide, and chance did not open it
in 89 million samples; it had to be opened deliberately. See "Rate, not just
existence" below.

## P1.3b — capacity was not sampled with the magazine

### Root cause

`_umem_alloc`'s PTC magazine path obtained a magazine from
`umem_depot_alloc_trylock()` — which validates it against the magtype the cache
has *at that moment* — and then **separately** read
`cp->cache_magtype->mt_magsize` to decide how many rounds that magazine held:

```c
fmp = umem_depot_alloc_trylock(cp, &cp->cache_full);  /* capacity v1 */
new_magsize = cp->cache_magtype->mt_magsize;          /* v2, possibly > v1 */
mag->loaded = fmp;
mag->rounds = new_magsize;
buf = mag->loaded->mag_round[--mag->rounds];          /* indexes v2-1 */
```

`umem_cache_magazine_resize()` runs on the update thread and changes the magtype
between those two reads. A 127-round magazine then gets indexed as if it had
255 rounds — 1 KiB past the end of its own allocation, into the next chunk of
the same slab, which is another magazine. The pointer read from there is
returned to the caller as an allocation.

The free side had the same defect with the reads in the opposite order (magtype
first, magazine second), which desynchronizes the other way: a 255-round
magazine recorded as holding 127. That one does not index out of bounds, but it
puts a half-filled magazine on the depot's **full** list, whose contract is
"exactly magsize rounds", so `umem_depot_ws_reap()` frees the NULL tail slots to
the slab layer.

Reachable in a default build: `umem_cache_update()` schedules
`UMU_MAGAZINE_RESIZE` from ordinary depot contention, with no involvement from
the `umem_magazine_tuning` option.

### Fix

Capacity is derived from the magazine itself. A magazine is an object of some
`umem_magazine_<N>` cache, so its own slab header names that cache, whose
`cache_bufsize` is `(N + 1) * sizeof (void *)` — the inverse of how
`umem_cache_init()` sizes those caches. `umem_mag_capacity()` recovers `N` from
the magazine alone, and no resize can change it.

The magazine and the capacity it is indexed with are therefore one decision:
the window does not exist rather than being narrowed. `loaded` and `previous`
can legitimately be of different magtypes (a resize only has to land between two
refills), so each carries its own capacity — `magsize` and the new `pmagsize` —
and the two travel with their magazine across the loaded/previous swap.
`umem_ptc_mag_check()` asserts the invariant at each depot transfer.

### Pre-fix failure

Control `prefix-p13b`: only the capacity-source lines reverted, everything else
— probe, gate, instrumentation — identical to HEAD, so the comparison is
like-for-like. On `arm-hi@ptc2`, 96 threads:

| Build | capacity desyncs | outcome |
|---|---:|---|
| pre-fix (`prefix-p13b`) | **3,133,215** | **SIGSEGV** |
| post-fix (`HEAD`) | 0 | PASS |

Every pre-fix desync was the same shape, and it is exactly the defect:

```
CAPACITY DESYNC (loaded): recorded magsize=255 true=127 rounds=128
```

A 127-round magazine described as having 255, with observed round counts of 128
and above — i.e. indexing past the end of the magazine's own allocation — and
the process then died of SIGSEGV. That is the out-of-bounds access itself, not a
proxy for it. Excerpt:
`docs/results/prefix-evidence/2026-09-22-p1.3b-capacity-desync-prefix.log`.

Post-fix on the same box and the same gate: 0 desyncs with 132–145 threads
parked inside the window across the resize, at 96 and 192 threads.

### Rate, not just existence — and what the test does and does not prove

Two things could not detect this, and both were measured rather than assumed:

**ASan cannot see it, structurally.** Magazines are objects inside umem's own
mmap-backed slabs. There is no redzone between one magazine and the next, and
this tree contains no ASan poisoning anywhere. An overrun from one magazine into
its neighbour is, to ASan, an ordinary write to a valid heap page. An ASan build
runs both regressions clean and reports nothing (verified, x86_64).

**Chance cannot reach it.** The window is the few instructions between obtaining
the magazine and reading the capacity, and a cache resizes **at most once per
process** — a magtype only ever grows, and the 512 B class has exactly one step
available (127 → 255). So an unaided run gets one chance to land a resize inside
a ~20 ns window:

| Attempt | Samples | Desyncs |
|---|---:|---:|
| unaided, 96 threads, arm-hi, defect present | 67,443,588 | 0 |
| 200 µs delay per magazine load, defect present | 89,197,014 | 0 |

The delay failed because this workload performs only a few hundred *depot*
magazine loads in 25 s (the PTC bins absorb nearly everything): ~47 ms of open
window against one instant in 25 s.

So the window is opened by construction. Under `-DUMEM_PTC_RESIZE_PROBE` — which
is compiled out of every normal build, leaving not even a global load — a thread
that has just obtained a magazine **parks** inside the window and publishes that
it is there. The test waits until threads are parked, forces the magtype change
while they hold old-magtype magazines, then releases them. Parking there is safe:
`umem_depot_alloc_trylock()` has already released `ml_lock`, so a parked thread
holds no allocator lock and cannot block the update thread's resize; the wait is
bounded at 30 s. The probe changes no decision and performs no store the library
does not — the resize is the ordinary contention-scheduled one, and the desync is
the library's own arithmetic.

**Therefore this regression is a mechanism demonstration, not a
production-frequency measurement.** It establishes that the window is real, that
the consequence is an out-of-bounds access that crashes, and that the fix closes
it. It does *not* establish that this happens often in practice, and the
zero-in-67-million figure above is the honest statement about that. The
gating only fires because a test thread holds threads inside a window that
production code passes through in nanoseconds. A run without the probe now
reports INCONCLUSIVE rather than PASS, because a clean run there is not evidence.

## P1.3c — populated magazines were discarded

### Root cause

`umem_ptc_mag_return()` and `umem_ptc_mag_return_trylock()` checked
`UMEM_MAGAZINE_VALID` and, on a magtype mismatch, freed only the magazine
**shell**:

```c
if (UMEM_MAGAZINE_VALID(cp, mp)) {
        umem_depot_free(cp, mlp, mp);
} else {
        mag_cache = <mp's own slab cache>;
        _umem_cache_free(mag_cache, mp);   /* objects inside lost */
}
```

`_umem_free`'s "both magazines full" path calls that with the **full loaded
magazine**. So after a resize changes the magtype, the first thread to fill its
magazine destroys 127 objects: their only reference is gone while the slab layer
goes on counting them as allocated, so the slab holding them can never be freed.

The same paths also pushed a **populated** `previous` magazine onto the depot's
**empty** list on a size change. That loses the contents just as surely, only
less visibly: `umem_depot_ws_reap()` destroys empty-list magazines with
`full_rounds == 0`, so it never looks at the rounds inside.

### Fix

Both functions now take the round count, and two invariants are enforced at the
shared function rather than at each call site:

1. **Nothing is discarded with objects still in it.** A magazine whose magtype
   no longer matches cannot go back on a depot list, but its contents are live:
   drain to the slab layer first, then free the shell.
2. **The full/empty classification is the caller's count, not a guess.** A
   magazine goes on the full list only when it is *exactly* full; anything else
   is drained and goes on the empty list. This is what the depot's two lists
   actually promise, and inferring it from `rounds > 0` at a point where the
   count may be stale is what let a populated magazine onto the empty list.

`umem_ptc_mag_flush_all()` is simplified accordingly — it hands both magazines
over with their counts and lets the shared function do the draining.

### Pre-fix failure

Control `prefix-p13c`: only the drain and classification reverted; the ledger
observation point is identical to HEAD, so the counts are directly comparable.

The oracle is exact and counted inside the library, at the one instant loss can
occur — how many objects are still in a magazine when its shell is freed:

| Build | shells freed | objects still inside when freed | verdict |
|---|---:|---:|---|
| pre-fix, run 1 | 1 | **127** | FAIL |
| pre-fix, run 2 | 3 | **381** | FAIL |
| post-fix, x86_64 (3 runs) | 2, 3, 3 | 0, 0, 0 | PASS |
| post-fix, aarch64 (3 runs) | 1, 1, 2 | 0, 0, 0 | PASS |

Exactly 127 objects per discarded magazine — the full magazine capacity, which
is what the defect predicts. No statistics involved.

### Two measurement dead ends, recorded because they were nearly reported as results

**The `umem_ptc_enabled = 0` control is wrong for this defect.** It is the right
control for P1.3a and this test borrowed it, but turning the PTC off *moves* the
retention rather than removing only the defect: with the PTC off, freed objects
pile into per-CPU magazines that `umem_reap()` cannot drain; with it on, thread
exit drains the PTC completely. Different retention structures, so the floors
are not comparable. On a **fixed** build the PTC-off control came out 64, 64 and
1755 across three runs, swamping the defect and producing two spurious FAILs and
one PASS.

**Outstanding-buffer comparison is statistical and straddles its own margin.**
Even with the control changed to "identical round, no resize in it", the
test-minus-control difference on a **fixed** build came out −242/−88/+104 on
x86_64 and +340/+616 on aarch64, against a 512 margin — because per-CPU
magazine retention is not reachable by `umem_reap()` and varies with machine
width. Rather than widen the margin until the test stopped disagreeing with
itself, the exact ledger became the oracle. The comparison is still reported as
corroboration, and still gates the result in a non-probe build where it is the
only signal available, with that caveat recorded in the source.

## Both regressions initially failed to discriminate

Both passed against a pre-fix control on first writing. Recorded because the
diagnosis matters more than the outcome:

| Regression | Why it passed pre-fix | Fixed by |
|---|---|---|
| P1.3c | Gate opened before threads parked, so the resize landed during the ramp and threads parked already holding new-magtype magazines — the discard path was never entered. Log signature: test-round outstanding-while-parked *lower* than the control's (1172 vs 2190), because the purge inside the resize had already run. | Suppress the resize for the whole ramp in both rounds; open it only after every thread has parked and the magtype is confirmed unchanged |
| P1.3b | Detection looked at the wrong state — the test sampled its own PTC *between* operations, and a desynchronized magazine is typically replaced before the next sample. `ptc_checks` counted calls, not magazine loads, so "clean" and "never ran" were indistinguishable. | Observe in the library at the instant the capacity is recorded; add a refill counter so "the path never ran" is a distinct INCONCLUSIVE |

Both tests now refuse to report PASS when the window was not opened, which is
what let the original versions look green.

## Throughput

Concurrency oracle, `c7i.2xlarge`, 8 threads, 20 s, three runs each.

The A/B is against `prefix-both` — both fixes reverted, **everything else
identical to HEAD** — so only `umem.c` differs. A baseline of `4a89d91` would
have been meaningless here: the oracle binary itself changed by 377 lines
between that ref and HEAD (another agent's Phase 2 work), and it duly reported
67–71 Mops/s for `multi` against ~20 on both arms of this A/B. Comparing those
would have measured the benchmark rewrite, not the allocator.

| Workload | pre-fix (`prefix-both`) | post-fix (`fc6f32a`) |
|---|---|---|
| multi | 20.6, 20.3, 23.3 Mops/s | 15.9, 20.3, 18.4 Mops/s |
| prodcons | 0.7, 0.7, 0.7 Mops/s | 0.7, 0.7, 0.7 Mops/s |
| churn | 1.0, 1.0, 1.0 Mops/s | 1.0, 1.0, 1.0 Mops/s |

**No performance claim is made, in either direction.** `multi` spans 15.9–23.3
Mops/s across six runs of two builds, and 15.9–20.3 within the three runs of a
*single* build — a ±12 % spread on one binary, wider than any gap between the
arms. Three runs on a shared 8-vCPU instance cannot resolve a difference smaller
than that. `prodcons` and `churn` are identical to the reported precision.

For what it is worth mechanically, the fix replaces a load of
`cp->cache_magtype->mt_magsize` with a load of the magazine's own slab header —
both once per depot transfer, not per allocation, and the slab header is already
on the path to the magazine. There is no reason to expect a measurable
difference, and this data does not show one.

## Found but not fixed

**P1.3a's margin is tighter than its noise, on x86_64.** `make check` does not
run it, but `test_ptc_thread_exit_drain` intermittently FAILs. Measured on
`c7i.2xlarge`, matched samples:

| Build | runs | FAIL rate | mean PTC arm | mean control arm |
|---|---:|---:|---:|---:|
| baseline `4a89d91` | 15 | 1/15 (7 %) | 151 | 196 |
| postfix `fc6f32a` | 29 | 5/29 (17 %) | 147 | 66 |

The PTC arm — the thing under test — is unchanged (151 → 147). What moved is the
**control** arm (196 → 66), which tightens the fixed 192 margin and makes the
same underlying noise cross it more often. A lower control arm means the PTC-off
path now retains less, which is the direction a drain fix pushes; it is not
evidence that exiting threads are losing objects. The test pre-dates my work and
already failed at baseline (1/15), so this is a pre-existing marginal oracle, not
a regression introduced here — but the honest statement is that my change made an
already-marginal test fail more often, and I am not claiming the increase is
harmless. It needs an exact oracle of the kind P1.3c now has, instead of a
fixed threshold on a difference of two noisy growth measurements. Not fixed:
`umem_ptc.c`'s drain logic is correct and untouched; the test's oracle is the
problem, and rewriting a P1.3a regression was outside this task.

**The `umem_ptc_mag_check()` assertions are compiled out in release builds.**
They use `ASSERT()`, which `misc.h` defines away under `NDEBUG`. The invariant
they check is the one P1.3b broke, so it is worth having, but it defends debug
builds only. The regression does not rely on them — it checks the invariant
independently, in the test and in the probe — so this is a defence-in-depth gap,
not a verification gap.

**Not investigated:** the `vm.max_map_count` heap ceiling
(`docs/results/2026-09-22-umem-heap-ceiling-vma.md`) is deliberately unassigned
and was not touched. No allocation failures were seen in any run here
(`alloc_failures=0` throughout, including 355 M allocations at 96 threads).
