## Opportunity 1: Enable PTC for LD_PRELOAD

### Current State

**Problem:** Per-Thread Cache (PTC) generates optimized assembly for malloc/free but is disabled when using LD_PRELOAD because the interpose layer intercepts calls before PTC can handle them.

**Evidence:**
```
malloc() [interpose wrapper]
  → state checks + TLS guard (30-50 cycles)
  → umem_malloc()
    → PTC code unreachable
    → full magazine layer (20-40 cycles)
Total: 50-90 cycles
```

**Measurements:**
- With PTC: 20M ops/s (50ns per alloc+free)
- Without PTC: 6M ops/s (161ns per alloc+free)
- Overhead: 3.3x slower

### Proposed Solution

**Approach 1: Generate PTC in interpose layer**

Modify umem_genasm.c to generate assembly stubs in malloc_interpose.c instead of umem.c:

```c
// malloc_interpose.c
void *malloc(size_t size) {
    // Fast path generated by umem_genasm
    if (size <= 256 && likely(ptc_ready)) {
        // Generated: load from per-thread magazine
        // Generated: return object
        return ptc_fast_path(size);
    }

    // Slow path
    return umem_malloc(size);
}
```

**Approach 2: Use IFUNC resolvers**

Use GNU IFUNC to switch malloc implementation after initialization:

```c
void *malloc_init(size_t size);
void *malloc_ptc(size_t size);  // Generated by umem_genasm

void *malloc(size_t size) __attribute__((ifunc("malloc_resolver")));

static void *(*malloc_resolver(void))(size_t) {
    if (umem_ptc_enabled)
        return malloc_ptc;
    else
        return malloc_init;
}
```

### Expected Impact

**Improvement:**
- Throughput: 60-70% increase for small allocations
- Latency: 50-60% reduction in median case
- P99 latency: 40-50% reduction

**Benchmark targets:**
- Before: 6.22M ops/s (161ns) for 64-byte malloc/free
- After: 15-18M ops/s (55-65ns) for 64-byte malloc/free
- Goal: Match PTC direct-link performance

### Implementation

**Effort:** High (2-3 weeks)

**Tasks:**
1. Modify umem_genasm.c to emit code in interpose layer
2. Add ptc_ready flag in interpose layer
3. Handle state transitions correctly
4. Add architecture-specific code for aarch64, riscv64
5. Test on all platforms
6. Benchmark and tune

**Complexity:**
- Requires understanding of umem_genasm internals
- Must handle initialization race conditions
- Platform-specific assembly generation
- Complex interaction between interpose and PTC

**Risks:**
- Correctness issues during initialization
- Race conditions between threads
- Platform-specific bugs
- May not work on all architectures

**Testing strategy:**
```bash
# Stress test with threads
for i in {1..1000}; do
    ./test/bench/bench_allocators -a umem -w multi -t 16 -n 100000 || exit 1
done

# Verify PTC is active
objdump -d .libs/libumem_malloc.so | grep -A 20 "<malloc>" | grep ptc
```

### Status

**Not started**

**Blockers:**
- Requires deep understanding of umem_genasm architecture
- Need clear specification of interpose layer ABI
- Platform testing infrastructure needed

**Next steps:**
1. Study umem_genasm.c implementation
2. Prototype for x86_64 only
3. Measure improvement
4. Extend to other architectures if successful

## Opportunity 2: Lock-free Magazine Depot

### Current State

**Problem:** Magazine depot uses pthread mutexes for synchronizing magazine exchanges between threads. With 16+ threads, lock contention becomes severe.

**Evidence:**
```
umem_alloc/free performance:
- 1 thread: 4.59M ops/s
- 8 threads: 6.70M ops/s (1.5x, should be 8x)
- 16 threads: 3.95M ops/s (0.9x, REGRESSION!)
- 32 threads: 4.37M ops/s (1.0x, NO SCALING)
```

**Profiling shows:**
- pthread_mutex_lock in top 5 functions
- umem_depot_alloc has high lock wait time
- Cache line bouncing on depot lock variables

### Proposed Solution

**Approach: Lock-free stack with CAS**

Replace mutex-protected magazine lists with lock-free stacks using atomic compare-and-swap:

```c
typedef struct umem_maglist {
    umem_magazine_t *mag;
    struct umem_maglist *next;
} umem_maglist_t;

// Lock-free push
void depot_push_lockfree(umem_depot_t *depot, umem_magazine_t *mag) {
    umem_maglist_t *node = alloc_node();
    node->mag = mag;

    umem_maglist_t *old_head;
    do {
        old_head = atomic_load(&depot->head);
        node->next = old_head;
    } while (!atomic_compare_exchange(&depot->head, &old_head, node));
}

// Lock-free pop
umem_magazine_t *depot_pop_lockfree(umem_depot_t *depot) {
    umem_maglist_t *old_head, *new_head;
    do {
        old_head = atomic_load(&depot->head);
        if (!old_head)
            return NULL;
        new_head = old_head->next;
    } while (!atomic_compare_exchange(&depot->head, &old_head, new_head));

    umem_magazine_t *mag = old_head->mag;
    free_node(old_head);
    return mag;
}
```

**Alternative: Per-CPU magazines**

Eliminate depot entirely by providing per-CPU magazine sets (see Opportunity 6).

### Expected Impact

**Improvement:**
- Multi-threaded throughput: 50-100% increase at 16+ threads
- P99 latency: 60-80% reduction (eliminates lock waits)
- Thread scaling: Linear up to 32+ threads

**Benchmark targets:**
- Before: 3.95M ops/s at 16 threads
- After: 8-12M ops/s at 16 threads (2-3x improvement)
- Goal: Linear scaling up to 32 threads

### Implementation

**Effort:** Very High (4-6 weeks)

**Tasks:**
1. Design lock-free depot data structure
2. Implement atomic operations for all platforms
3. Handle ABA problem (use generation counters)
4. Memory reclamation strategy (hazard pointers or EBR)
5. Extensive testing for race conditions
6. Performance tuning and cache line alignment
7. Fallback to locked version if atomics unavailable

**Complexity:**
- Lock-free programming is notoriously difficult
- ABA problem requires careful handling
- Memory reclamation is complex (when to free maglist nodes?)
- Must work on all architectures (x86, ARM, RISC-V)
- Very hard to test (race conditions are non-deterministic)

**Risks:**
- HIGH RISK: Subtle correctness bugs
- Data races leading to corruption
- ABA problem causing use-after-free
- Performance may not improve if cache effects dominate
- May actually be slower on some platforms

**Testing strategy:**
```bash

make clean
CFLAGS="-fsanitize=thread" make
./test/bench/bench_allocators -a umem -w multi -t 32 -n 10000000

# Stress test with many iterations
for i in {1..10000}; do
    ./test/bench/bench_allocators -a umem -w multi -t 16 -n 100000 || exit 1
done

# Validate with formal verification tools (if available)
# Run benchmarks on multiple platforms
```

### Status

**Not started**

**Blockers:**
- High complexity and risk
- Requires lock-free programming expertise
- Extensive testing infrastructure needed
- May require academic collaboration

**Next steps:**
1. Research lock-free allocator literature (TCMalloc, jemalloc)
2. Prototype simple lock-free stack

## Opportunity 3: Optional Recursion Guard

### Current State

**Problem:** TLS recursion guard adds 8-12 cycles (3 TLS accesses) to every allocation to prevent deadlock during pthread_create on some platforms.

**Evidence:**
```assembly
# malloc hot path
mov    0x2cee(%rip),%rdx        # Load TLS offset
mov    %fs:(%rdx),%eax          # TLS read #1
lea    0x1(%rax),%ecx           # Increment
mov    %ecx,%fs:(%rdx)          # TLS write #1
test   %eax,%eax                # Check recursion
# ... allocation ...
subl   $0x1,%fs:(%rdx)          # TLS write #2
```

**Measurements:**
- tools/measure_overhead shows TLS overhead: 0 cycles per access (cached)
- But hot path analysis shows 4 TLS instructions = 8-12 cycles
- Microbenchmark: 30-40% overhead attributed to guard

### Proposed Solution

**Make recursion guard conditional at build time:**

```c
// malloc_guard.h
#ifdef ENABLE_RECURSION_GUARD
    #define UMEM_ENTER_MALLOC() umem_enter_malloc()
    #define UMEM_EXIT_MALLOC() umem_exit_malloc()
#else
    #define UMEM_ENTER_MALLOC() 0
    #define UMEM_EXIT_MALLOC() ((void)0)
#endif

// malloc_interpose.c
void *malloc(size_t size) {
    if (UMEM_ENTER_MALLOC() > 0) {
        UMEM_EXIT_MALLOC();
        return bootstrap_malloc(size);
    }

    void *ret = umem_malloc(size);
    UMEM_EXIT_MALLOC();
    return ret;
}
```

**Runtime detection:**

Add configure-time check for pthread_create deadlock:

```bash
# configure.ac
AC_MSG_CHECKING([if pthread_create deadlocks with umem])
AC_RUN_IFELSE([
    # Test program that creates thread during malloc
    # If deadlocks, enable guard by default
], [
    AC_DEFINE([ENABLE_RECURSION_GUARD], [1])
    AC_MSG_RESULT([yes, enabling guard])
], [
    AC_MSG_RESULT([no, guard optional])
])
```

### Expected Impact

**Improvement:**
- Throughput: 30-40% increase for guarded code
- Latency: 30-40% reduction in median case
- Overhead: Reduces by 8-12 cycles per allocation

**Benchmark targets:**
- Before: 161ns per malloc+free (with guard)
- After: 110-120ns per malloc+free (without guard)
- Goal: Match or beat glibc malloc

### Implementation

**Effort:** Low (2-3 days)

**Tasks:**
1. Add ENABLE_RECURSION_GUARD configure option
2. Add conditional compilation to malloc_guard.h
3. Add configure-time deadlock detection test
4. Update documentation
5. Test on multiple platforms
6. Provide safe defaults (guard enabled unless proven safe)

**Complexity:**
- Very simple change (mostly #ifdef)
- Well-understood problem
- Easy to test

**Risks:**
- LOW RISK: Deadlock on platforms that need the guard
- Mitigation: Default to guard enabled
- Provide clear documentation on when safe to disable

**Testing strategy:**
```bash
# Test without guard
./configure CFLAGS="-DDISABLE_RECURSION_GUARD"
make clean && make

# Stress test pthread_create
for i in {1..1000}; do
    UMEM_DEBUG="" LD_PRELOAD=.libs/libumem_malloc.so \
    tools/quick_test || echo "DEADLOCK at iteration $i"
done

# If no deadlocks after 1000 runs, safe to use
```

### Status

**Not started**

**Blockers:**
- None (can implement immediately)
- Need to test on multiple platforms

**Next steps:**
1. Add configure option (1 day)
2. Test on Linux, macOS, FreeBSD
3. Document platforms where safe
4. Benchmark improvement
5. Release as experimental feature

**Recommendation:** Implement this first (low-hanging fruit).

## Opportunity 4: IFUNC State Resolution

### Current State

**Problem:** Every malloc checks interpose_state to ensure initialization is complete, adding 3-5 cycles per allocation.

**Evidence:**
```assembly
# malloc hot path
mov    0x41c2(%rip),%eax        # Load interpose_state
cmp    $0x2,%eax                # Compare with INTERPOSE_READY
jne    slow_path                # Branch if not ready
```

**Measurements:**
- State check adds 3-5 cycles (memory load + compare + branch)
- Branch is well-predicted after startup
- But still on critical path

### Proposed Solution

**Use GNU IFUNC to switch implementations after initialization:**

```c
// malloc_interpose.c
void *malloc_before_init(size_t size) {
    // Handle initialization
    // Check state, bootstrap allocations, etc.
    return umem_malloc(size);
}

void *malloc_after_init(size_t size) {
    // Fast path only (no state checks)
    if (UMEM_ENTER_MALLOC() > 0) {  // Still need guard
        UMEM_EXIT_MALLOC();
        return bootstrap_malloc(size);
    }

    void *ret = umem_malloc(size);
    UMEM_EXIT_MALLOC();
    return ret;
}

// IFUNC resolver runs once at load time
static void *(*malloc_resolver(void))(size_t) {
    umem_init();  // Ensure initialization
    return malloc_after_init;
}

void *malloc(size_t size) __attribute__((ifunc("malloc_resolver")));
```

### Expected Impact

**Improvement:**
- Throughput: 20-30% increase after initialization
- Latency: 10-15% reduction in median case
- Overhead: Removes 3-5 cycles from hot path

**Benchmark targets:**
- Before: 161ns with state checks
- After: 140-145ns without state checks
- Goal: Remove branch misprediction risk

### Implementation

**Effort:** Medium (1 week)

**Tasks:**
1. Implement IFUNC resolvers for malloc/free/calloc/realloc
2. Handle platforms without IFUNC support (fallback)
3. Ensure thread-safety during resolution
4. Test initialization edge cases
5. Benchmark and tune

**Complexity:**
- IFUNC is platform-specific (GNU extension)
- Must handle non-IFUNC platforms (macOS, BSD)
- Interaction with LD_PRELOAD may be tricky
- Must ensure atomic transition

**Risks:**
- MEDIUM RISK: Initialization races
- Not portable to all platforms
- May not work with LD_PRELOAD (need testing)
- Dynamic linker complexity

**Testing strategy:**
```bash
# Test on platforms with IFUNC
./configure && make
./test/bench/bench_allocators -a umem -w single -n 1000000

# Test on platforms without IFUNC
./configure --host=aarch64-apple-darwin && make
./test/bench/bench_allocators -a umem -w single -n 1000000

# Stress test initialization
for i in {1..1000}; do
    LD_PRELOAD=.libs/libumem_malloc.so ./test/bench/bench_allocators -a umem -w single -n 100 || exit 1
done
```

### Status

**Not started**

**Blockers:**
- Need to verify IFUNC works with LD_PRELOAD
- Need fallback for non-IFUNC platforms

**Next steps:**
1. Research IFUNC + LD_PRELOAD interaction
2. Prototype on x86_64 Linux
3. Measure improvement
4. Add fallback for other platforms

## Opportunity 5: Optimize TLS Access

### Current State

**Problem:** Each allocation accesses TLS variables multiple times (recursion depth, PTC state), adding overhead.

**Evidence:**
```c
// Current implementation
__thread int umem_malloc_recursion_depth = 0;

void *malloc(size_t size) {
    umem_malloc_recursion_depth++;  // TLS write
    if (umem_malloc_recursion_depth > 1) {  // TLS read
        // ...
    }
    // ...
    umem_malloc_recursion_depth--;  // TLS write
}
```

**Measurements:**
- 4 TLS accesses per allocation (2 reads, 2 writes)
- Each access: 2-4 cycles
- Total: 8-16 cycles overhead

### Proposed Solution

**Option 1: Group TLS variables in single cache line**

```c
// Group all TLS data in one struct
typedef struct {
    int recursion_depth;
    umem_cache_t **ptc_caches;
    uint64_t stats[4];  // Padding to 64 bytes
} umem_tls_t;

__thread umem_tls_t umem_tls __attribute__((aligned(64)));

// Single TLS base load, then offset access
void *malloc(size_t size) {
    umem_tls_t *tls = &umem_tls;  // One TLS load
    tls->recursion_depth++;        // Offset access
    // ...
    tls->recursion_depth--;
}
```

**Option 2: Use compiler-optimized TLS**

```c
// Use __thread with initial-exec model (faster)
__thread int umem_malloc_recursion_depth __attribute__((tls_model("initial-exec"))) = 0;
```

**Option 3: Minimize TLS accesses**

```c
// Load once, use multiple times
void *malloc(size_t size) {
    int depth = umem_malloc_recursion_depth;  // Load once
    umem_malloc_recursion_depth = depth + 1;  // Use loaded value

    if (depth > 0) {
        umem_malloc_recursion_depth = depth;
        return bootstrap_malloc(size);
    }

    void *ret = umem_malloc(size);
    umem_malloc_recursion_depth = depth;  // Restore
    return ret;
}
```

### Expected Impact

**Improvement:**
- Throughput: 15-25% increase
- Latency: 10-20% reduction
- Overhead: Reduces by 4-8 cycles per allocation

**Benchmark targets:**
- Before: 161ns with multiple TLS accesses
- After: 135-145ns with optimized TLS
- Goal: Minimize TLS overhead

### Implementation

**Effort:** Medium (1 week)

**Tasks:**
1. Refactor TLS variables into single struct
2. Benchmark different TLS models (local-exec, initial-exec)
3. Ensure cache line alignment
4. Test on multiple platforms
5. Verify no regressions

**Complexity:**
- Requires understanding of TLS implementation
- Platform-specific behavior (Linux vs BSD vs macOS)
- Must maintain thread-safety
- May interact with dynamic loading

**Risks:**
- LOW RISK: Should not affect correctness
- TLS models may not be portable
- Initial-exec may not work with LD_PRELOAD

**Testing strategy:**
```bash
# Benchmark TLS overhead directly
tools/measure_overhead 100000

# Compare before/after
./test/bench/bench_allocators -a umem -w single -n 1000000
```

### Status

**Not started**

**Blockers:**
- Need to understand TLS model restrictions

**Next steps:**
1. Profile TLS access patterns
2. Benchmark different TLS models
3. Implement grouped TLS struct
4. Measure improvement

## Opportunity 6: Per-CPU Magazines

### Current State

**Problem:** Magazines are per-thread, causing:
- Thread migration invalidates cache locality
- Cross-thread deallocation bypasses PTC
- Depot contention when threads > CPUs

**Alternative:** Per-CPU magazines (like Linux SLUB allocator)

### Proposed Solution

**Per-CPU magazine arrays:**

```c
// One magazine per CPU (not per thread)
typedef struct {
    umem_magazine_t *loaded;
    umem_magazine_t *previous;
    int cpu_id;
} umem_cpu_mag_t;

static umem_cpu_mag_t *cpu_magazines[MAX_CPUS];

void *umem_cache_alloc_percpu(umem_cache_t *cp, int flags) {
    int cpu = getcpu();  // Get current CPU
    umem_cpu_mag_t *cpu_mag = cpu_magazines[cpu];

    // Fast path: allocate from CPU-local magazine
    if (cpu_mag->loaded->rounds > 0) {
        return cpu_mag->loaded->objs[--cpu_mag->loaded->rounds];
    }

    // Slow path: refill magazine
    // ...
}
```

### Expected Impact

**Improvement:**
- Multi-threaded throughput: 100-200% increase
- Thread migration overhead: Eliminated
- Cross-thread deallocation: Better handled

**Trade-offs:**
- Requires CPU affinity or getcpu() syscall
- More complex than per-thread caching
- May not help if threads > CPUs

### Implementation

**Effort:** Very High (6-8 weeks)

**Tasks:**
1. Design per-CPU magazine data structure
2. Implement getcpu() or CPU affinity detection
3. Handle CPU hotplug (add/remove CPUs)
4. Rewrite magazine layer
5. Extensive testing
6. Performance tuning

**Complexity:**
- Fundamental architecture change
- Requires OS-specific code (getcpu varies by platform)
- Must handle CPU migration
- Complex interaction with scheduler

**Risks:**
- HIGH RISK: Large code changes
- May not improve performance if getcpu() is slow
- CPU migration may be frequent on some workloads
- Compatibility with all platforms unclear

### Status

**Not started (research phase)**

**Blockers:**
- Requires research into per-CPU allocators
- Need to prototype getcpu() overhead

**Next steps:**
1. Research Linux SLUB allocator design
2. Benchmark getcpu() overhead on various platforms
3. Prototype simple per-CPU cache
4. Evaluate performance improvement
5. Decide if worth full implementation

## Opportunity 7: Batch Allocation API

### Current State

**Problem:** Applications allocating many objects of same size pay per-allocation overhead N times.

**Current API:**
```c
void **objs = malloc(N * sizeof(void*));
for (int i = 0; i < N; i++) {
    objs[i] = malloc(size);  // N function calls
}
```

### Proposed Solution

**Batch allocation API:**

```c
// Allocate N objects at once
int umem_cache_alloc_bulk(umem_cache_t *cp, int flags, void **objs, int n) {
    umem_magazine_t *mag = current_thread_mag(cp);

    // Fast path: allocate from magazine in batch
    if (mag->rounds >= n) {
        memcpy(objs, &mag->objs[mag->rounds - n], n * sizeof(void*));
        mag->rounds -= n;
        return n;
    }

    // Slow path: refill magazine and retry
    // ...
}

// Usage
void *objs[100];
int allocated = umem_cache_alloc_bulk(my_cache, 0, objs, 100);
```

### Expected Impact

**Improvement:**
- Batch allocation: 5-10x faster than individual allocations
- Amortizes fixed overhead over batch
- Better cache locality

**Use cases:**
- Network packet buffers
- Database row objects
- Batch processing systems

### Implementation

**Effort:** Low (1 week)

**Tasks:**
1. Add umem_cache_alloc_bulk() API
2. Add umem_cache_free_bulk() API
3. Optimize magazine access for batches
4. Add documentation
5. Add benchmarks

**Complexity:**
- Simple API addition
- Magazine layer already supports batching
- Easy to implement and test

**Risks:**
- LOW RISK: Optional API, no effect on existing code

### Status

**Not started**

**Next steps:**
1. Design API
2. Implement for umem_cache only (not malloc)
3. Benchmark improvement
4. Document use cases

## Opportunity 9: Memory Prefetching

### Current State

**Problem:** Magazine refills may miss in cache, causing latency spikes.

**Current code:**
```c
void *umem_cache_alloc(umem_cache_t *cp, int flags) {
    umem_magazine_t *mag = get_magazine(cp);
    if (mag->rounds > 0) {
        return mag->objs[--mag->rounds];  // May miss in cache
    }
    // Refill magazine (slow path)
}
```

### Proposed Solution

**Prefetch next object:**

```c
void *umem_cache_alloc(umem_cache_t *cp, int flags) {
    umem_magazine_t *mag = get_magazine(cp);
    if (mag->rounds > 0) {
        void *obj = mag->objs[--mag->rounds];

        // Prefetch next object
        if (mag->rounds > 0) {
            __builtin_prefetch(mag->objs[mag->rounds - 1], 0, 3);
        }

        return obj;
    }
    // Refill magazine
}
```

**Prefetch during magazine refill:**

```c
void refill_magazine(umem_cache_t *cp, umem_magazine_t *mag) {
    // Allocate objects from slab
    for (int i = 0; i < mag_size; i++) {
        mag->objs[i] = slab_alloc(cp);

        // Prefetch next slab
        if (i < mag_size - 1) {
            __builtin_prefetch(next_slab(cp), 0, 3);
        }
    }
}
```

### Expected Impact

**Improvement:**
- P99 latency: 5-15% reduction (fewer cache misses)
- Throughput: 5-10% increase
- Reduces variance in allocation latency

### Implementation

**Effort:** Medium (1-2 weeks)

**Tasks:**
1. Identify cache miss locations (use perf)
2. Add prefetch hints
3. Benchmark improvement
4. Tune prefetch distance
5. Test on multiple CPUs (Intel, AMD, ARM)

**Complexity:**
- Simple concept but tricky to tune
- Prefetch may hurt if done wrong
- Platform-specific behavior

**Risks:**
- LOW RISK: Can be disabled if no improvement
- May pollute cache if over-prefetched

### Status

**Not started**

**Next steps:**
1. Profile cache misses with perf
2. Identify high-miss locations
3. Add prefetch hints
4. Benchmark improvement

## Opportunity 10: Slab Preallocation

### Current State

**Problem:** First allocation from a cache may need to allocate slab, causing latency spike.

### Proposed Solution

**Preallocate slabs at cache creation:**

```c
umem_cache_t *umem_cache_create(const char *name, size_t size, ...) {
    umem_cache_t *cp = create_cache_struct(...);

    // Preallocate N slabs
    for (int i = 0; i < initial_slab_count; i++) {
        umem_slab_t *slab = allocate_slab(cp);
        add_to_free_list(cp, slab);
    }

    return cp;
}
```

**Improvement:**
- First allocation: 5-10x faster (no slab allocation)
- P99 latency: 5-10% reduction (fewer slow paths)

**Trade-off:**
- Increased memory usage at startup
