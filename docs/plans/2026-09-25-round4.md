## P5.13b -- mangle magazine-round pointers
`mag_round[]` in `umem_magazine_t` holds raw object addresses; the per-thread
bins are safe-linked (P5.13) but the magazine layer behind them is not. The
magazine lives in `umem_ptc_cache`/magazine slabs (NOT a user size-class
slab), so it is not one overrun away from a user buffer -- this is why it was
deferred, not urgent. Reuse `UMEM_SLOT_MANGLE`/`umem_link_cookie` (hidden
visibility already set). Sites: grep `mag_round` and COUNT before starting
(plan said ~25). Every reader demangles, every writer mangles:
`_umem_cache_alloc`/`_umem_cache_free` (the CPU-layer fast paths),
`umem_cache_alloc_batch`/`umem_cache_free_batch`, `umem_mag_drain`,
`umem_depot_destroy_stale`, `umem_magazine_destroy`, `umem_mag_init_fast`
(this WRITES NULLs -- a mangled NULL is not NULL, so the "is this slot empty"
readers must compare against MANGLE(slotp, NULL), or init must write the
mangled form; decide and be consistent), `umem_inspect.c` cached-set builder,
`umem_introspect.c`, `tools/umem.c`, the gdb/lldb scripts (out-of-process --
they must demangle with the cookie read from the target; if that is too much,
gate the mangle so the tools still work OR teach the scripts the transform).
Regression: `test/security/test_mag_round_mangle` -- overwrite a round in a
loaded magazine with a chosen address, next alloc of that class must NOT
return it; FAILs under `-DUMEM_NO_LINK_MANGLE`. Cost: one XOR per CPU-layer
alloc/pop -- A/B it; ship even at single-digit percent (7a) but record the
number. The `mag_init_fast`-writes-NULL question is the real design point:
get it right or the depot silently corrupts.

## P7.4 -- exact span table (DECIDED: jemalloc's answer)
Replace the convex-hull accept-anything-between-spans in `umem_may_own()` with
an exact sorted span table, published the way `vmem_heap_lo/hi` are
(release-store on append, lock-free read). Spans only ever grow.
- `vmem_span_create()` (vmem.c) already publishes `vmem_heap_lo/hi`; extend it
  to append (base,len) to a global sorted array under `vm_lock`, version-
  stamped or seqlock'd so `umem_may_own` reads it lock-free.
- `umem_may_own()` (umem_own.c / malloc.c): binary search the table; a heap
  pointer short-circuits on the lo/hi bounds first (pays nothing new), only a
  foreign or between-spans pointer pays the ~log2(N) loads (~7 at a 9 GB heap
  of 4 MiB qcache slabs).
- Regression: `test/security/test_forged_span_gap` -- a forged `MALLOC_MAGIC`
  header in a caller `mmap` placed BETWEEN two heap spans; `free()` must refuse
  it (today it is accepted onto a PTC bin and later returned). FAILs at the
  parent, PASSes after.
- Hot-path A/B: the free path. A heap free must be within the null (short-
  circuit). Measure a foreign-free microbench too (that is where the search
  runs). ship_ab_arms + hotpath_ab with `-m`.
- Watch: span REMOVAL. If a span can be torn down (arena destroy), the table
  needs a tombstone or the read can see a freed span. Check whether
  `vmem_span_create`'s spans are ever unmapped during process life; if yes,
  the lock-free read needs the same publish discipline on removal (or accept
  that a torn-down span reads as owned briefly -- state it).

## P8.5b REFRAMED -- arm the rseq lock-free reload (the documented next lever)

IMPORTANT: P8.5b is NOT a from-scratch owning-thread-free redesign. The
2026-09-09 sustained-contention diagnosis already halved the p999 gap
(156->85 us) with the trylock fix and named the remaining lever precisely:
the rseq lock-free per-CPU reload path, which EXISTS in umem_rseq.c /
umem_rseq_x86_64.S / umem_rseq_aarch64.S but is INERT (nothing loads a
magazine into cache_rseq[cpu].loaded_mag, so the fast path always finds
rounds==0 and falls through to the cc_lock + depot path). Arming it lets the
common case skip the magazine layer and the depot scan entirely on a hit --
that is what closes the tail.

Read BEFORE any code, in full:
- docs/results/2026-09-09-rseq-reload-analysis-v2.md (why C-only and
  lock-based arming are UNSAFE -- the migration-safety gap -- and the six
  pre-existing fast-path bugs already fixed as prerequisites)
- docs/results/2026-09-09-rseq-reload-asm-design.md (the PRECISE
  implementation spec for the asm-based reload; this is the design, already
  done -- implement it, do not redesign it)
- docs/results/2026-09-09-sustained-depot-contention-diagnosis.md sec 7

The work is: implement the asm-reload per that spec on BOTH arches, arm it
(wire the reload to populate cache_rseq[cpu].loaded_mag), and verify:
- the six-bug regression suite (test/unit/test_rseq_fastpath.c,
  test/stress/repro_rseq_trailing_store.c) still passes;
- stress_concurrency_oracle 192t/60s default + --enable-asan, BOTH metal
  arches, 0 aliasing/corruption -- this is the mandatory soundness gate;
- sustained p999 on metal beats the 85 us it is at now, toward the
  ~25 us size-class-allocator tier;
- the uncontended fast path (t=1) is not regressed (A/B).
If the asm reload cannot be made migration-safe as specced, or regresses the
oracle, it stays INERT and the outcome is "spec implemented, measured,
reverted, here is why" -- an acceptable result IF the oracle evidence is on
the record. This is the highest-risk item; asm on two arches, kernel rseq
semantics, a 192-thread correctness gate. Design-first was already done; the
gate is the discipline.

## P8.5b OLD framing (superseded, kept for context) -- owning-thread free
The sustained-load 8-19x t=192 gap and the 19 us p999 tail are the depot's
all-to-all mutex exchange: a freed object goes to the FREEING cpu's stripe,
wanted next by whichever cpu allocates, so at N threads the depot is N-way
through per-stripe mutexes. jemalloc/mimalloc/etc. return a freed object to
the OWNING thread's page/segment as a lock-free push. This is a redesign, not
a patch. DESIGN DOC FIRST (`docs/plans/2026-09-25-p85b-owning-thread-free.md`):
- Where does "owning thread/cpu" come from for a umem object? A slab knows its
  cache; does a buffer cheaply know its home magazine/cpu? Probably not today.
- Options: (a) per-cpu lock-free free stack (Treiber) that the owning cpu
  drains -- MPSC, cheap push, but needs a home-cpu tag per object or per slab;
  (b) remote-free queue per cpu that the update thread or next local alloc
  drains. Cost: the tag, and the drain cadence.
- Invariants: fork safety (another unordered push path -- see P1.3d),
  exit-drain exactness (the P1.3a/P1.3d oracles count hand-offs), no new UAF
  window, no double-free when owning cpu drains concurrently with a remote push.
- Do NOT write code until the design doc names the tag, the push/drain
  protocol, the fork rule, and the regression. Then a minimal prototype behind
  a flag, A/B on metal at t=192 (the only place the win shows), and only ship
  if it beats the depot without regressing the fast path or the oracles.
- This may end as "characterised, prototype measured, deferred" if the tag
  cost eats the fast path. That is an acceptable outcome IF measured.
