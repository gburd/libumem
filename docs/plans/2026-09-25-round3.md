## Per-item briefs

### P5.13 -- mangle PTC bin slots and magazine rounds
glibc safe-links tcache entries (`PROTECT_PTR`: `ptr ^ (&slot >> 12)`).
libumem's `pool[]` slots and `mag_round[]` are raw pointers. P5.4 already
has `UMEM_LINK_MANGLE(slotp, val) = val ^ umem_link_cookie ^ (slotp >> 12)`
and `umem_link_cookie` from `AT_RANDOM`; reuse it exactly. Sites: the bin
push/pop in `_umem_alloc`/`_umem_free` (umem.c ~3906-3930, ~4116-4125),
`umem_ptc.c`'s bin flush/refill (`bin->slots[...]`), the child fork drain,
`umem_ptc_destroy`. Magazine rounds: `mag_round[]` is also read by the CPU
layer (`_umem_cache_alloc/free`), `umem_mag_drain`, `umem_depot_destroy_stale`,
`umem_magazine_destroy`, `umem_inspect.c`'s cached-set builder and
`umem_introspect.c` -- every reader must demangle; grep `mag_round` and count
before starting (expect ~25 sites). Decide: bins only (cheap, covers the
P5.12 structure) or bins+magazines (covers the depot too). Start with bins;
measure; then magazines as a separate commit with its own A/B. Regression:
`test_freelist_mangle.c`'s `inslab` pattern applied to a PTC slot: overwrite
`ptc->pool[k]` with a chosen address from the same thread, next `umem_alloc`
of that class must NOT return it (mangled: returns garbage -> caught by
containment or faults on a poisoned page; test via a `-DUMEM_NO_LINK_MANGLE`
build that FAILS). Cost budget: glibc pays one XOR per push/pop; if the A/B
shows > 1 % at t=1 the answer is still yes (AGENTS.md 7a) but say so.

### P6.3b -- `umem_cache_free_batch` holds `cc_lock` across depot trips
Metal table in P6.3's STATUS: 163 us/thread at 16k vs 85 per-object. Read
`umem_cache_free_batch` (umem.c). Hypothesis: it fills `cc_loaded`, and when
that fills it calls `umem_depot_free`/`umem_depot_alloc` WITHOUT dropping
`cc_lock`, so the depot trip (and any slab-layer fallthrough) happens under
the lock other threads on that CPU need. Fix candidates: (a) release
`cc_lock` around the depot exchange, re-take, re-validate `cc_magsize`
(the pattern `_umem_cache_free` uses for the "allocate a new magazine" case);
(b) batch straight to the depot as a full magazine when the batch >= magsize.
Measure: `probe_threads 4000` on lo (parity expected), then 16000 on
`intel-hi` ONCE, both builds, same session. Target: <= per-object drain
(85 us) at 16k; state the number either way.

### P6.4b (3) -- size per-CPU state by online CPUs, not pow2
`umem_max_ncpus` rounds 192 -> 256. Eight sites do `(cpu + i) & (ncpus - 1)`
(umem.c ~2473-2764, `umem_depot_alloc_trylock`/`free_trylock`/`alloc`/
`free`). With the P8.2 hint a real cpu id, `& mask` is only needed for the
non-Linux fallback hash. Fix: keep `umem_max_ncpus` as the ARRAY size =
online count; index with `hint % ncpus` where `hint` may exceed (fallback
only) and `(cpu + i) % ncpus` in the steal loops -- OR keep pow2 for the
steal stride and size only `cache_cpu[]`/depot arrays to online. Measure
per-cache bytes on 192 CPUs (117 KB today) and the steal loop's insn/op
(a `div` vs an `and`; if > 1 % use a 256-entry indirection table). Only
worth doing on metal; do it in the same metal session as P6.3b.

### P6.4b (4) -- fork() 3.0 s at 50k caches
`umem_lockup_cache` takes 771 mutexes per cache. Idle-cache shortcut: a
cache with `cc_loaded == NULL` on every CPU and empty depot lists has no
per-CPU state to make consistent. Invariant to PROVE before shipping: after
`cache_lock` is taken in lockup, can a cache go idle -> non-idle?
`_umem_cache_alloc` takes `cc_lock` (not `cache_lock`) and may then load
`cc_loaded` from the depot -- so yes, without `cc_lock` a thread can be
mid-load. Therefore the shortcut is NOT sound for the parent's consistency;
it IS sound if the child discards per-CPU state for caches it finds
half-loaded (leak, not corruption) -- which is P1.3d's rule 2 applied to
the CPU layer. Write this up either way; implement only with a regression
that forks under allocation load with 1000+ caches and checks the child
via the P1.3a stranded counter. If not provable, record and close as
characterised.

### P8.5 tail -- `umem_slab_alloc` per-object `cache_lock`
Post-0532c38 profile (P8.5 STATUS): `native_queued_spin_lock_slowpath`
5.6 % (mmap_lock on slab creation), `umem_slab_alloc` 3.2 % +
`pthread_mutex_lock` 2.1 %. frag's live set grows, so depot misses fall to
the slab layer one object at a time under `cache_lock`. Fix: `umem_slab_alloc`
variant that carves N objects under one `cache_lock` into a magazine (the
plan's original (1) "batch-from-slab"). Regression: sustained frag t=8
p999 (19 us today vs glibc 2) and the `cache_lock` acquisition count under
the probe build. Hot path only on the miss side; A/B anyway.

### P8.2c -- measure, then maybe bound
`probe_threads 4000 --size 4096` and `8192` (add the flag if absent) on lo.
If RSS/thread approaches the 5.4 MB worst case, byte-bound the XLARGE tier's
magazines (63 rounds x 8 KB = 504 KB per magazine is the problem; 15 rounds
at 4-8 KB is what the Solaris table had). Commit with the measurement.

### P7.4 -- decision only
Write into Phase 7: exact span table (sorted, published like
`vmem_heap_lo/hi`, binary search on the free path -- ~5 loads) vs
unforgeable header (per-process secret folded into `malloc_stat`; changes
the on-heap format and every reader in `umem_inspect.c`/tools). State which
and why; not for this release.
