## Coordinator finding: UMEM_SLAB_MEMBER has the T6 bound (2026-09-27)

`UMEM_SLAB_MEMBER(sp, buf)` (umem_impl.h:486) accepts `[slab_base, slab_base +
cache_slabsize)`. `slab_base` already includes the colour offset, so the range
runs `colour` bytes past the slab into the next page, the same defect as T6
(fixed in whatis by bounding by `slab_chunks * chunksize`). Five callers:

| site | what it guards | reachable consequence of the wide bound |
|---|---|---|
| umem.c:1974 `umem_slab_free` (non-hash) | the free-path bad-address check | none via the wide tail: `sp = UMEM_SLAB(cp, buf)` is derived from buf's own aligned block, so buf is always inside that slab. But MEMBER never checks chunk ALIGNMENT, so a free() of an interior pointer or a pointer into the colour gap / slab header passes and is linked onto the freelist |
| umem.c:1652 `umem_slab_link_valid` (P5.4) | a demangled freelist link must name a buffer of this slab | the wide tail lets a forged link point `colour` bytes into the NEXT slab page, and it is also not chunk-aligned: a weaker P5.4 containment check than claimed |
| umem.c:1162 `umem_findslab` | debug/verify lookup | can name the wrong slab (the T6 symptom) |
| umem.c:1934 | ASSERT | debug only |

Action: tighten MEMBER to the chunk range and add a chunk-alignment test
(`(buf - slab_base) % chunksize == 0`) on the free and link-valid paths, each
with a regression that fails first (interior-pointer free; forged link into
the colour tail). This is a hardening change on the free path, so it needs the
hot-path A/B. Assigned to a follow-up agent (@r7member).

## T9 diagnosis landed (8cf5f9e) -> T9 fix plan

Cause: x86_64 getpcstack() walks the %rbp chain only; libumem is built
without -fno-omit-frame-pointer (gcc 14 -O2 omits them), so %rbp holds data
after frame 0 and the P5.9 bounds check correctly stops the walk at depth 1.
aarch64 is fine (depth 10). Second defect: the walker never skips libumem's
own frames, so frames #0-#2 are always the allocator even with frame pointers.
Third: learn records bufsize (224), not request size (200).
Fix (one agent, @r7t9fix): (1) -fno-omit-frame-pointer in AM_CFLAGS, with a
hot-path A/B (distros cite 1-2 %; measure it); (2) skip frames whose PC is in
libumem's own text range when recording; (3) learn records the request size;
(4) correct tools/DEBUGGING.md (it claims backtrace(3)/DWARF on Linux).

## T1/T8 hook: NOT merged at 1.9-17.2 % (x86) / 2.8-6.0 % (arm) hooks-off cost

@r7hook (dfebc815): fix works (all three XFAIL -> PASS, both arches), on
origin/r7hook-fix (a59e7d6 + 0969f59), not merged. A/B with hooks OFF: every
point outside its null, +4-7 % insn/pair. Cause (read from a59e7d6): the hook
is a CALLSITE on the fast path -- `_umem_free` tests UMEM_HOOKS_ON() and may
call umem_hook_free before its NULL exit, so the compiler saves callee-saved
registers on every free; `_umem_alloc` became wrapper + always-inline body
with the hook after the body, so the PTC-hit return value must survive a
potential call. A load + branch is cheap; a reachable call on the fast path
is not.

Redesign (coordinator decision): keep the fast path call-free.
- When hooks go on, force allocations off the PTC/magazine fast paths onto
  the existing slow path (which already calls umem_introspect_break_check),
  instead of adding a call to the fast path. The fast path already has one
  "not eligible" gate: umem_ptc_bin_table[] returns -1 for debug caches.
  Turning hooks on can flip that gate (or a single flag the bin lookup already
  loads), so every allocation and free takes the slow path, where the hook
  call lives and costs nothing when off.
- The hooks are a debugging feature; making allocation slower WHILE a
  debugger has events or a break armed is acceptable and expected.
- Gate: the same three scripts pass; hooks-off A/B inside the null, t=1 and
  t=8, both arches. If the gate cannot be flipped soundly for threads already
  holding PTC bins, drain/bypass is the design question; say so.
