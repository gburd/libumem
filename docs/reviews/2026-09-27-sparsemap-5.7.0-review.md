# sparsemap v5.6.0 → v5.7.0: dependency review

**Verdict: libumem does not take v5.7.0.** Upstream 5.7.0 fixes both
regressions 5.6.0 introduced, but it adds five new defects of its own. It
also leaves open two of the four 5.6.0 defects this project reported, and
another that predates 5.6.0. None of this reaches libumem, because libumem
never calls sparsemap (§1 of the 5.6.0 review).

The vendored copy (v5.5.0, byte-identical) is being removed in v4.0.0, per
the round-7 decision in `docs/plans/2026-09-27-round7.md`. v3.3.x keeps
v5.5.0 unchanged.

The upstream report, which stands alone and contains no libumem context, is
`/tmp/sparsemap-bug-report.md`. It is reproduced as
[§4](#4-the-upstream-report). Its combined reproducer is
[`2026-09-27-sparsemap-5.7.0-probe.c`](2026-09-27-sparsemap-5.7.0-probe.c),
also at `/tmp/sparsemap-repro.c`. Nothing was changed, committed or branched
in the upstream repo.

## 3. What libumem does

- **v3.3.x:** keeps sparsemap v5.5.0, byte-identical, and unreachable from
  libumem code. No change here: this is a review-only task, and libumem's
  build is untouched.
- **v4.0.0:** removes `sm.c`/`sm.h` and the dead `test/common.[ch]`
  (workstream B in round 7). After that, libumem vendors no sparsemap, and
  future sparsemap releases stop being a libumem review item.
- Were it ever re-vendored:
  - #3, #4, #5, #6 and #8 would each be blocking for an embedder that
    persists maps or uses fixed buffers.
  - D4 would be blocking for libumem's own small-stack rules.
  - The condition would be a release with report items 1–8 fixed,
    and this probe exiting 0 apart from the INFO lines.

##### 1. `sm_is_subset`, `sm_is_superset` and `sm_overlap` are still O(cardinality)

5.6.0 made `sm_equals` and the rest of the set algebra run-based. These three
were not converted, and 5.7.0 leaves them unchanged (`sm.c:7466`, `:7488`,
`:7494`). Each still walks `sm_next_member` one bit at a time.

Build: `cc -std=c11 -D_GNU_SOURCE -O2 -I$SM -o t t.c $SM/sm.c && ./t`

```c
#include <sm.h>
#include <stdint.h>
#include <stdio.h>
#include <time.h>

static double
secs(void)
{
	struct timespec t;
	clock_gettime(CLOCK_MONOTONIC, &t);
	return t.tv_sec + t.tv_nsec / 1e9;
}

int
main(void)
{
	/* 24 valid bytes: one RLE chunk at 0, capacity = length = 2^31 - 1 */
	uint64_t w[3] = { 1, 0,
		0x4000000000000000ULL | (0x7FFFFFFFULL << 31) | 0x7FFFFFFFULL };
	sm_t *a = sm_open_copy((uint8_t *)w, sizeof w, 0);
	sm_t *s = sm_create(64);
	sm_add(s, (1ULL << 31) + 5);
	double t = secs();
	int eq = sm_equals(a, a);
	printf("sm_equals(a,a)    = %d  %.3f s\n", eq, secs() - t);
	t = secs();
	int ov = sm_overlap(a, s);
	printf("sm_overlap(a,s)   = %d  %.3f s\n", ov, secs() - t);
	fflush(stdout);
	t = secs();
	int sub = sm_is_subset(a, a);
	printf("sm_is_subset(a,a) = %d  %.3f s\n", sub, secs() - t);
	return 0;
}
```

Observed on 5.7.0: `sm_equals` 0.000 s and `sm_overlap` 10.0 s (x86_64) /
10.3 s (aarch64). `sm_is_subset` took 18.5 s on aarch64; on x86_64 it was
still running when the 30 s harness timeout killed the process. 5.6.0 is
the same (`sm_overlap` 9.4 s, `sm_is_subset` 17.5–19.7 s). On 5.5.0,
`sm_equals` also takes 17 s.
Expected: all three under 1 ms, as `sm_equals` already is.

**Fix (verified).** Route both functions through the run-based helpers that
already exist:

```c
bool sm_is_subset(const sm_t *a, const sm_t *b)   /* after the NULL/empty guards */
{	return (!sm_nonempty_difference(a, b)); }
bool sm_overlap(const sm_t *a, const sm_t *b)     /* after the NULL/empty guards */
{	return (sm_intersection_cardinality(a, b) != 0); }
```

Applied to 5.7.0, both calls take 0.2–0.5 ms (about 1 ms under ASan) on
both architectures. The probe's oracle fuzz still passes, including subset
and overlap on random pairs: 0 failures in 103,500 checks at `-O2` and
34,500 under ASan+UBSan. Upstream's suite still passes 18/18 under
ASan+UBSan. Both helpers use the 33 KB iterator of item 2, so this trades
time for stack until item 2 is fixed. An early-exit sweep would be faster
still; this change is only the minimal one. `sm_add_range`, `sm_remove_range` and `sm_flip_range` are
also bit-by-bit, but those are bounded by the caller's `[lo, hi)`.

##### 2. ~33 KB stack frames: `sm_equals` of two 1-bit maps overflows a 24 KiB stack

`__sm_run_iter_t` (`sm.c:7576–7595`) embeds `run_lo[1025]` and
`run_hi[1025]`, 16.4 KB, and it is a local variable. With `gcc -O2
-fstack-usage` there are seven frames of 16 KB or more; 5.5.0 had none, and
its largest frame was 1.8 KB.

| function | 5.5.0 | 5.6.0 (x86_64) | 5.7.0 x86_64 | 5.7.0 aarch64 |
|---|---|---|---|---|
| `sm_xor` | <1.8 KB | 33,520 | 33,568 | 33,536 |
| `__sm_run_pair_counts` (all `*_cardinality`, `sm_jaccard_index`, `sm_nonempty_difference`) | — | 33,056 | 33,120 | 33,104 |
| `sm_compare`, `sm_subset_compare` | <1.8 KB | 33,040 | 33,104 | 33,088 |
| `sm_equals` | <1.8 KB | 33,008 | 33,072 | 33,056 |
| `sm_extract_range` | <1.8 KB | 17,008 | 17,024 | 17,008 |
| `sm_hash` | <1.8 KB | 16,512 | 16,544 | 16,560 |

Build: `cc -std=c11 -D_GNU_SOURCE -O2 -I$SM -o t t.c $SM/sm.c && ./t` (the frame table: `gcc -std=c11 -D_GNU_SOURCE -O2 -fstack-usage -c -I$SM $SM/sm.c && sort -t$'\t' -k2 -nr sm.su | head`)

```c
#include <sm.h>
#include <stdio.h>
#include <sys/mman.h>
#include <ucontext.h>

#define STACK (24 * 1024)
#define GUARD (64 * 1024)
static ucontext_t main_ctx, co_ctx;
static int eq = -1;

static void
body(void)
{
	sm_t *a = sm_create(64), *b = sm_create(64);
	sm_add(a, 1);
	sm_add(b, 1);
	eq = sm_equals(a, b);
}

int
main(void)
{
	/* a 24 KiB coroutine stack with a 64 KiB PROT_NONE guard below it */
	char *m = mmap(NULL, GUARD + STACK, PROT_READ | PROT_WRITE,
	    MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
	mprotect(m, GUARD, PROT_NONE);
	getcontext(&co_ctx);
	co_ctx.uc_stack.ss_sp = m + GUARD;
	co_ctx.uc_stack.ss_size = STACK;
	co_ctx.uc_link = &main_ctx;
	makecontext(&co_ctx, body, 0);
	swapcontext(&main_ctx, &co_ctx);
	printf("sm_equals({1},{1}) on a 24 KiB stack = %d\n", eq);
	return 0;
}
```

Observed: 5.5.0 prints `= 1`. 5.6.0 and 5.7.0 die with **SIGSEGV** on both
architectures.
Expected: `= 1`. Any caller on a coroutine, fiber or small thread stack is
affected.

**Suggested fix (not verified).** Decode one run at a time from the chunk
descriptor instead of filling a 1025-entry array per chunk. The iterator
then needs a chunk pointer, a slot index and a bit offset. Alternatively,
heap-allocate the arrays once per call.

##### 3. 5.7.0 serializes a form that 5.6.x rejects ("mutually readable" is one-way)

The 5.7.0 CHANGELOG says: "No wire-format change (still version 2, mutually
readable with 5.6.x); a drop-in source swap". But `sm_serialize` of any map
held in small-set mode writes a body whose first word has bit 63 set
(`sm.c:8898` also sets header byte 6). `SM_WIRE_VERSION` is still 2
(`sm.c:8855`), so a 5.6.x reader accepts the header and then rejects the
body.

Build: `cc -std=c11 -D_GNU_SOURCE -O2 -I$SM -o t t.c $SM/sm.c && ./t`, once with `SM` = a 5.7.0 tree and once with a 5.6.0 tree.

```c
#include <sm.h>
#include <stdint.h>
#include <stdio.h>

/* What 5.7.0's sm_serialize writes for {5,70} on a little-endian host. */
static const uint8_t v570[40] = {
	0x73, 0x6d, 0x31, 0x30, 0x02, 0x01, 0x01, 0x00, 0x02, 0, 0, 0, 0, 0, 0, 0,
	0x02, 0, 0, 0, 0, 0, 0, 0x80, 0x20, 0, 0, 0, 0, 0, 0, 0,
	0x40, 0, 0, 0, 0, 0, 0, 0 };

int
main(void)
{
	sm_t *m = sm_create(64);
	sm_add(m, 5);
	sm_add(m, 70);
	uint8_t out[64];
	size_t n = sm_serialize(m, out, sizeof out);
	printf("%s sm_serialize({5,70}) = %zu bytes:", SM_VERSION_STRING, n);
	for (size_t i = 0; i < n; i++)
		printf(" %02x", out[i]);
	sm_t *d = sm_deserialize(v570, sizeof v570);
	printf("\nsm_deserialize(5.7.0 bytes of {5,70}) = %s\n",
	    d == NULL ? "NULL" : (sm_cardinality(d) == 2 &&
	        sm_contains(d, 5, NULL) && sm_contains(d, 70, NULL)) ?
	                             "{5,70}" : "WRONG");
	return 0;
}
```

Observed: 5.7.0 writes the 40 bytes above. 5.5.0 and 5.6.0 write 56 bytes
(a v2 chunk stream), and `sm_deserialize` of the 5.7.0 bytes returns
**NULL** on 5.5.0 and 5.6.0. For the raw body, `sm_open` leaves an empty
map on 5.5.0 and 5.6.0, and `sm_open_copy` returns NULL (5.6.0) or a wrong
map (5.5.0). 5.7.0 reads 5.6.x bytes correctly.

Expected: either a 5.6.x reader decodes it, or the version changes so the
reader can say why. Data written by a 5.7.0 node and read by a 5.6.x node
(rolling upgrade, replica, on-disk file) is dropped.

**Suggested fix.** Either (a) bump `SM_WIRE_VERSION` to 3 whenever the body
is small-set, keeping v2 output for chunk-mode maps, and document that 5.6.x
cannot read v3; or (b) have `sm_serialize` always materialize small maps to
the v2 chunk form. That is what 5.6.x can read, at a cost of 16 bytes for
`{5,70}`. Either way, correct the CHANGELOG sentence.

##### 4. `sm_add` into a fixed buffer fails with ENOSPC although the chunk form fits

`__sm_add_dispatch` (`sm.c:5353–5369`) tries the flat small form first for
any index below 1024. When the flat form does not fit in the capacity, it
returns `SM_IDX_MAX`/`ENOSPC` (`sm.c:5368`) without trying the smaller
chunk form. The flat form needs `8 + (idx/64 + 1)·8` bytes, 136 for index
1000, while one sparse chunk needs 32.

Build: `cc -std=c11 -D_GNU_SOURCE -O2 -I$SM -o t t.c $SM/sm.c && ./t`

```c
#include <sm.h>
#include <stdint.h>
#include <stdio.h>

int
main(void)
{
	/* (a) fixed caller buffer, no grow */
	uint64_t buf[12];
	sm_t *m = sm_wrap((uint8_t *)buf, sizeof buf); /* 96 bytes */
	sm_clear(m);
	uint64_t rc = sm_add(m, 1000);
	printf("sm_wrap(96 B): sm_add(1000) = %s, size %zu B\n",
	    rc == 1000 ? "1000" : "SM_IDX_MAX (ENOSPC)", sm_get_size(m));
	/* (b) growable map */
	sm_t *g = sm_create(64);
	sm_add_grow(&g, 5);
	sm_add_grow(&g, 64);
	sm_add_grow(&g, 900);
	printf("sm_create(64) + sm_add_grow {5,64,900}: capacity %zu B, "
	    "size %zu B\n", sm_get_capacity(g), sm_get_size(g));
	return 0;
}
```

Observed on 5.7.0: `sm_add(1000) = SM_IDX_MAX (ENOSPC), size 8 B`, and
capacity **4096 B** for 48 bytes of data. On 5.5.0 and 5.6.0: `sm_add(1000)
= 1000, size 32 B`, capacity 64 B.

Expected: `sm_add` succeeds whenever the map's chunk encoding fits, as it
did in 5.6.0. `sm_wrap`/`sm_init`/`sm_open` users with fixed-size buffers
(for example, a map embedded in a fixed-size page or record) can no longer
store an index they could store in 5.6.0.

**Suggested fix.** On `__sm_small_add` failure, fall through to the
chunk-mode path (promote, then `__sm_map_set`) instead of returning ENOSPC.

Caveat: we tried exactly that change (`goto` the chunk path, with
`if (small)` changed to `if (__sm_is_small(map))`). It fixes the snippet
above, but upstream's `test_smallset_api.c:439` and `:675` then fail. The
cause is that `sm_add_grow` no longer grows 64 → 4096 bytes, so a later
`sm_remove`/`sm_pop_first` hits the chunk path's documented ENOSPC headroom
requirement. 5.6.0 returns the same ENOSPC for the same sequence
(`sm_create(64)`, add `{5,64,900}`, `sm_remove(900)`). So the two tests
depend on the 4 KiB over-growth. The fix needs those tests to use
`sm_remove` with growth, or `sm_remove` to need less headroom.

##### 5. Small-set reads allocate, give wrong answers on malloc failure, and are ~180× slower

In small mode, `sm_rank` (`sm.c:10669`), `sm_select` (`:10504`), `sm_span`
(`:10691`), `sm_scan` (`:5836`), `sm_offset` (`:6715`) and `sm_statistics`
(`:8773`) call `__sm_materialize`. That function builds a chunk-mode copy
with one `sm_add_grow` per set bit, then frees it. It happens on every call.
When the allocation fails, these functions return values that are legal
results but wrong: `0`, `SM_IDX_MAX`, or no callback. `sm_union`,
`sm_intersection` and `sm_difference` also materialize every small-mode
operand (`sm.c:9013`, `:9336`, `:9687`).

Build: `cc -std=c11 -D_GNU_SOURCE -O2 -I$SM -o t t.c $SM/sm.c && ./t`

```c
#include <sm.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

static int fail;
static unsigned long calls;
static void *my_malloc(size_t n) { calls++; return fail ? NULL : malloc(n); }
static void *my_realloc(void *p, size_t n) { calls++; return fail ? NULL : realloc(p, n); }

int
main(void)
{
	sm_t *m = sm_create(64);
	sm_add(m, 5);
	sm_add(m, 70);
	sm_add(m, 71);
	sm_allocator_t hooks = { my_malloc, my_realloc, free };
	sm_set_allocator(hooks);
	(void)sm_rank(m, 0, 1023, true);
	printf("allocator calls made by one sm_rank: %lu\n", calls);
	fail = 1;
	printf("malloc failing: sm_rank(0,1023)=%zu (expect 3) "
	    "sm_select(1)=%llu (expect 70)\n",
	    sm_rank(m, 0, 1023, true),
	    (unsigned long long)sm_select(m, 1, true));
	return 0;
}
```

Observed on 5.7.0: `1` allocator call per `sm_rank`, and with malloc failing
`sm_rank = 0`, `sm_select = 18446744073709551615`. On 5.5.0 and 5.6.0: `0`
calls, `3` and `70`.

Cost per call (probe R5; 264 random bits below 1024, `-O2`), 5.7.0 vs
5.6.0:

| | x86_64 5.7.0 | x86_64 5.6.0 | aarch64 5.7.0 | aarch64 5.6.0 |
|---|---|---|---|---|
| `sm_rank` | 19,683 ns | 109 ns | 21,013 ns | 96 ns |
| `sm_select` | 19,728 ns | 115 ns | 21,080 ns | 140 ns |
| `sm_union` | 38,068 ns | 261 ns | 40,762 ns | 323 ns |
| `sm_contains` | 2 ns | 54 ns | 2 ns | 51 ns |

Expected: read-only queries do not allocate, and never return a wrong
answer.

**Suggested fix.** Implement rank, select, span and scan directly on the
word array. Each is a few lines of popcount and ctz. For the binary
operations, compute small×small word-wise, and small×chunk by expanding the
small operand into one on-stack chunk.

##### 6. `sm_difference` emits an RLE chunk at an unaligned start: the result is invalid and cannot be reloaded

When both operands have an RLE chunk at the same start and `b`'s run covers
a prefix of `a`'s, the both-RLE branch of `sm_difference`
(`sm.c:9452–9502`) emits the survivor through `__sm_emit_chunk_bits`. For
an RLE source, that calls `__sm_append_rle_chunk(result, emit_start, …)`
with the raw bit index (`sm.c:9258`), not a 2048-aligned chunk start. The
in-memory map answers membership correctly. But `sm_validate` rejects it,
because rule (b) requires aligned starts (`sm.c:8720`). So `sm_deserialize`
of its own `sm_serialize` output returns NULL, and `sm_open` of its bytes
yields an empty map.

Build: `cc -std=c11 -D_GNU_SOURCE -O2 -I$SM -o t t.c $SM/sm.c && ./t`

```c
#include <sm.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

int
main(void)
{
	sm_t *a = sm_create(1024), *b = sm_create(1024);
	sm_add_range(a, 2048, 5092);
	sm_add_range(b, 2048, 4698);
	sm_t *d = sm_difference(a, b); /* [4698, 5092) */
	size_t n = sm_serialized_size(d);
	uint8_t *buf = malloc(n);
	sm_t *rt = sm_deserialize(buf, sm_serialize(d, buf, n));
	printf("|d|=%zu sm_validate(d)=%d sm_deserialize(sm_serialize(d))=%s\n",
	    sm_cardinality(d), sm_validate(d), rt ? "ok" : "NULL");
	return 0;
}
```

Observed on 5.6.0 and 5.7.0: `|d|=394 sm_validate(d)=0
sm_deserialize(sm_serialize(d))=NULL`. The body is `01.. | 5a12000000000000
| 8a010000c5000040`, one RLE chunk at start 4698, capacity 394, length 394.
On 5.5.0: `|d|=394 sm_validate(d)=1 ... ok`. 5.5.0 emits the same bytes,
but its `sm_validate` has no alignment rule. It is the 5.6.0 validator that
exposes this.

Expected: every set-operation result is valid under the library's own
`sm_validate`.

Found by the attached fuzzer (`./repro 1 200 1000`, `sm_difference`). A
difference that leaves a hole in the middle of the run
(`[2048,5092) \ [3000,3100)`) is valid. `sm_union`, `sm_intersection` and
`sm_xor` over six unaligned RLE pairs all validate. Only `sm_difference`
failed (probe R12).

**Suggested fix (not verified).** An RLE chunk encodes a run that starts
at the chunk's own start, so a survivor that begins mid-window cannot be
one. In the RLE arm of `__sm_emit_chunk_bits`, split `[emit_start,
emit_end)` at the next 2048 boundary. Emit the head as a sparse chunk at
the aligned start (the words path), and only the aligned remainder with
`__sm_append_rle_chunk`. `__sm_emit_run` (`sm.c:6609`) already does exactly
this split for `sm_xor`/`sm_extract_range`.

##### 7. `sm_validate` accepts an RLE chunk of length 0, and readers disagree about it

`sm_validate` checks `length > capacity` (`sm.c:8731`) but not
`length == 0`. `__sm_chunk_rank` computes `end = length - 1`
(`sm.c:1653`), which underflows to `SIZE_MAX`, so every bit counts as set.
`sm_next_member` and `sm_contains` treat the chunk as empty.

Build: `cc -std=c11 -D_GNU_SOURCE -O2 -I$SM -o t t.c $SM/sm.c && ./t`

```c
#include <sm.h>
#include <stdint.h>
#include <stdio.h>

int
main(void)
{
	/* one RLE chunk at 0: capacity 2048, length 0 */
	uint64_t w[3] = { 1, 0, 0x4000000000000000ULL | (2048ULL << 31) | 0 };
	sm_t *m = sm_open_copy((uint8_t *)w, sizeof w, 0);
	if (m == NULL) {
		printf("rejected\n");
		return 0;
	}
	printf("sm_validate=%d sm_cardinality=%zu sm_is_empty=%d "
	    "sm_next_member=%s\n",
	    sm_validate(m), sm_cardinality(m), sm_is_empty(m),
	    sm_next_member(m, SM_IDX_MAX, NULL) == SM_IDX_MAX ? "none" : "a bit");
	return 0;
}
```

Observed (5.5.0, 5.6.0 and 5.7.0): `sm_validate=1 sm_cardinality=2048
sm_is_empty=0 sm_next_member=none`.
Expected: rejected, or cardinality 0.

**Fix (verified).** In `sm_validate`, reject an RLE chunk whose length is 0:

```diff
 		if (__sm_chunk_is_rle(&chunk) &&
-		    __sm_chunk_rle_get_length(&chunk) > capacity) {
+		    (__sm_chunk_rle_get_length(&chunk) == 0 ||
+		        __sm_chunk_rle_get_length(&chunk) > capacity)) {
```

With this change applied to 5.7.0, `sm_open_copy` rejects the chunk (probe
R6a), and upstream's suite still passes 18/18 under ASan+UBSan.

##### 8. Small-set mode does unaligned 8-byte loads and stores

`sm.h:599` requires an 8-byte-aligned buffer for `sm_wrap`, but says a
misaligned one "will work but with a perf penalty" on x86_64/aarch64, and
`sm.h:189` calls access "unaligned-safe regardless". The chunk code keeps
that promise through `__sm_load_u64`/`__sm_bitvec_unaligned_t`. The new
small-set helpers do not: `__sm_small_words()` returns a plain `uint64_t *`
(`sm.c:2367`), and reads go through it directly (`sm.c:2394`, `2406`,
`2446`, `2448`, `4212`, `4274`, `5320`, `5326`, `8695`).

Build: `cc -std=c11 -D_GNU_SOURCE -O1 -fsanitize=undefined -I$SM -o t t.c $SM/sm.c && ./t`

```c
#include <sm.h>
#include <stdint.h>
#include <stdio.h>

int
main(void)
{
	_Alignas(8) uint8_t raw[8 + 256] = { 0 };
	sm_t *m = sm_wrap(raw + 4, 256); /* 4-byte aligned, like VARDATA() */
	sm_clear(m);
	sm_add(m, 5);
	printf("contains(5)=%d\n", sm_contains(m, 5, NULL));
	return 0;
}
```

Build with `-fsanitize=undefined`. Observed on 5.7.0: `contains(5)=1`, plus
`runtime error: load of misaligned address ... for type 'uint64_t'` at the
lines above. 5.5.0 and 5.6.0 are clean.

Expected: no UB, as with the chunk form, which reads the same buffer
through `__sm_load_u64`.

**Suggested fix.** Access the small words through
`__sm_load_u64`/`__sm_store_u64`, or through the existing unaligned typedef.

##### 9. Note: `sm_hash` values changed again

Seam coalescing (`8221230`) changed `sm_hash([2000,2100))` from
`545d696894c49004` (5.6.0) to `5f78a413fd761504` (5.7.0). 5.5.0 gave
`f61b2a5d1cd7fcd5`. `{5,70}` and `[0,4096)` did not change between 5.6.0 and
5.7.0. This is a consequence of the correct fix for the encoding-dependent
hash, not a defect. It belongs in the CHANGELOG, though: a caller that
persists `sm_hash` (a hash index, a cache key) must rebuild on upgrade.
