## 3. Defects in v5.6.0 (report for upstream)

Probe results, identical on x86_64 and aarch64, at both `-O2` and
`-O1 -fsanitize=address,undefined`. There were no sanitizer reports, so every
failure below is a logic or cost failure, not memory corruption. Source:
`sm.c` sha256 `1c87ec52…` (v5.5.0) and `eac7a444…` (v5.6.0).

| Probe | v5.5.0 | v5.6.0 |
|---|---|---|
| P1 `sm_split` at an inter-chunk gap | PASS | **FAIL** |
| P2 `sm_equals`/`sm_hash`, RLE vs equivalent sparse | PASS | **FAIL** |
| P2, three library-only edit-history pairs | PASS | PASS |
| P3 `sm_equals(big,big)` | FAIL (>10 s) | PASS (0.2–1.1 ms) |
| P3 `sm_is_subset(big,big)` | FAIL (>10 s) | **FAIL (>10 s; >30 s under ASan)** |
| P3 `sm_overlap(big,{2^31+5})` | FAIL (8.9–9.5 s) | **FAIL (9.2–9.5 s; >30 s under ASan)** |

### D1 — regression: `sm_split` moves the lower chunk when `idx` is in an inter-chunk gap

```c
sm_t *m = sm_create(1 << 16), *o = sm_create(1 << 16);
sm_add(m, 1); sm_add(m, 8193);          /* chunks at 0 and 8192 */
sm_split(m, 5000, o);                   /* returns 5000 */
/* expected: m = {1},  o = {8193}
 * v5.5.0:   m = {1},  o = {8193}
 * v5.6.0:   m = {},   o = {1, 8193}    <- bit 1 is on the wrong side */
```

**Cause.** In phase (1), `ea1d45e` changed the `in_middle` test from
`start + cap > idx` to `start <= idx && start + cap > idx`. That fixed the
non-terminating loop. It also made the `start > idx` branch below it
reachable for the first time:

```c
if (start > idx) { src = prev; i--; break; }
```

That branch was dead code before: any chunk with `start > idx` already
satisfied `start + cap > idx` and set `in_middle`. Now it rewinds `src` one
chunk, so phase (5) moves the chunk *below* `idx` as well. Upstream's
`test_split_safety` case "chunk above the split point" did not catch this,
because it has only one chunk and `prev == src` there.

**One-line fix** (verified): drop the rewind, so the loop stops at the first
chunk that lies entirely above `idx` and phase (5) moves exactly the chunks
from there on:

```diff
 		if (start > idx) {
-			src = prev;
-			i--;
 			break;
 		}
```

With this change applied to v5.6.0, P1 passes and upstream's
`test_split_safety` still passes, both under ASan+UBSan (log
`intel-lo-r6sm-sm-diag`). `prev` then becomes a dead store.

### D2 — contract break: `sm_equals` and `sm_hash` depend on the encoding

`sm.h` documents `sm_equals` as "defined by content, not encoding (so an RLE
chunk and an equivalent sparse chunk encoding the same bits compare equal)".
It also says maps equal under `sm_equals` must hash equal.

```c
/* a: RLE chunk [0, 4096), built by sm_add_grow 0..4095 */
/* b: the same 4096 bits as two full sparse chunks (all 32 flags ONES),
 *    decoded by sm_open_copy and accepted by sm_validate: */
uint64_t w[5] = { 2, 0, ~0ULL, 2048, ~0ULL };
sm_t *b = sm_open_copy((uint8_t *)w, sizeof w, 256);
/* v5.5.0: sm_equals(a,b) = 1, hash(a) == hash(b)
 * v5.6.0: sm_equals(a,b) = 0, hash(a) != hash(b)   (bit-by-bit oracle says equal) */
```

**Cause.** `__sm_run_iter_t` deliberately does not merge runs across chunk
boundaries. It relies on the premise that "equal maps occupy the same chunks
and so decompose identically". That premise is false. An RLE chunk spans
many 2048-bit windows as one run, while the same bits stored as sparse chunks
decompose into one run per window. `sm_equals` compares run sequences and
`sm_hash` hashes run endpoints, so both disagree across encodings.
`sm_compare` and `sm_subset_compare` are unaffected: they advance by overlap,
not by run identity.

The three library-only pairs in P2 still pass: remove/re-add, `sm_xor` result
vs `sm_add` build, ascending vs descending build. So this has not yet been
shown from a map built purely by library mutators. It *is* reachable from
any valid decoded input, which is exactly the untrusted-input threat model
5.6.0 targets. A caller that uses `sm_hash` as a hash-table key with
`sm_equals` as the equality check, over decoded maps, gets false misses.

**Suggested fix (not verified).** Coalesce adjacent runs inside
`__sm_run_next`: keep reading while the next run's `lo` equals the current
`hi`, so the iterator yields maximal runs, as its own comment claims it does.
The iterator stays O(runs).

### D3 — S4 is incomplete: `sm_is_subset`, `sm_is_superset` and `sm_overlap` are still O(cardinality)

The CHANGELOG says the amplification class is closed. These three public
functions still walk `sm_next_member` bit by bit. On the 24-byte valid map
from upstream's own `test_amplify.c` (one RLE chunk,
`cap == len == 2^31 − 1`):

- `sm_is_subset(big, big)` does not finish in 10 s (30 s under ASan).
- `sm_overlap(big, {2^31 + 5})` takes 9.2–9.5 s.

These are the same inputs that 5.6.0 fixed for `sm_equals`, where the time
dropped to 0.2–1.1 ms. The functions that remain bit-by-bit are
`sm_is_subset`, `sm_is_superset` (a wrapper around it), `sm_overlap`,
`sm_add_range`, `sm_remove_range` and `sm_flip_range`. The range functions
are bounded by caller-supplied `[lo, hi)`, not by the input. Only
`sm_to_array` is documented as intentionally O(cardinality).

**Suggested fix.** `sm_is_subset(a, b)` is `!__sm_run_pair_counts`-style
`|a| > |a ∧ b|`. `sm_overlap` is `|a ∧ b| > 0`, with an early exit. Both
already have a run-based primitive in the file.

### D4 — cost: ~33 KB stack frames

The frames come from `__sm_run_iter_t`, which embeds two
`uint64_t[SM_CHUNK_MAX_CAPACITY/2 + 1]` arrays (16.4 KB), as a local.
`gcc -O2 -fstack-usage` on x86_64, largest frames:

| function | v5.5.0 | v5.6.0 |
|---|---|---|
| `sm_xor` | (bit loop) | **33,520 B** |
| `__sm_run_pair_counts` (all `*_cardinality`, `sm_jaccard_index`, `sm_nonempty_difference`) | — | **33,056 B** |
| `sm_subset_compare`, `sm_compare` | small | **33,040 B** |
| `sm_equals` | small | **33,008 B** |
| `sm_extract_range` | small | 17,008 B |
| `sm_hash` | small | 16,512 B |
| largest frame in the file | 1,776 B (`sm_offset`) | 33,520 B |

`.text` grows from 59,160 to 65,023 bytes. Upstream's README lists
PostgreSQL extensions and vendored PostgreSQL forks as its users. For a
library embedded in other processes, whose callers may run on small or
fixed-size thread stacks, a 2 × 16 KB iterator on the stack is a
regression. An iterator that decodes one run at a time from the chunk
descriptor needs a few words of state, not 16 KB.

### Not a defect, noted for upstream

- `sm.h` line 110 reads ` * * ## Allocation lineage and disposal`. The
  NULL-map section insertion swallowed the newline, so the stray `* *`
  breaks the Doxygen heading.
- Upstream's test suite passes at 12/12 with D1–D3 present. P1 and P2 would
  be worth adding to `test_split_safety.c` and `test_amplify.c`, and P3's
  `sm_is_subset`/`sm_overlap` timings to `test_amplify.c`.

### What 5.6.0 gets right

The memory-safety fixes are real and matter to anyone who feeds
`sm_open`/`sm_open_copy` untrusted bytes, or who mutates short RLE runs:

- `787940b`: shift UB, negative memmove, and `sm_add` corrupting a short RLE
  chunk.
- `ea1d45e`: over-read and over-write in `sm_split`.
- `1f7c418`: validation on open.

A fixed 5.6.1 should be taken.

## 4. Why libumem holds at v5.5.0

- **Nothing to gain.** No libumem code reaches any changed function (§1). The
  5.6.0 fixes protect callers that libumem does not have.
- **Something to lose.** D1 is a silent wrong-answer regression in a function
  that was correct in 5.5.0. D2 breaks a documented contract. D4 adds 33 KB
  frames to exported functions, which is exactly the small-stack hazard class
  libumem is currently fixing elsewhere.
- Shipping a known-regressed version under the libumem badge, in exchange
  for fixes to code nothing reaches, is the wrong trade. The v5.4.0 → v5.5.0
  rationale ("shipping known-broken third-party code under a libumem badge is
  not acceptable regardless") argues *against* v5.6.0 here.
- **Condition to re-vendor:** an upstream release with D1 and D2 fixed and the
  probe passing P1 and P2. D3 and D4 are desirable but not blocking for
  libumem, since it has no caller.

## 5. The `umem_sm_*` ABI surface

`nm -D --defined-only .libs/libumem.so.1.0.0` on a default build of
`ec1c98d` (verify-isolated, both arches). Log: `*-r6sm-sm-nm/out.log`.

| | x86_64 | aarch64 |
|---|---|---|
| total dynamic exports | 368 | 368 |
| `umem_sm_*` functions | **85** | **85** |
| `umem_sparsemap` (the `sparsemap()` constructor, prefixed) | 1 | 1 |
| unprefixed `sm_*` / `sparsemap*` / `__sm*` | 0 | 0 |
| `sm.o` `.text` | 58,168 B | 54,124 B |
| in-tree binaries referencing any `umem_sm_*` | 0 of 128 | — |

`libumem_malloc.so` defines none of these; it gets them through its `NEEDED`
dependency on `libumem.so.1`. `libumem.a` carries the same 85 as `T` symbols.

So libumem exports **86 functions (23% of its dynamic ABI) that it never
calls, and ships no header for.**

- The only "embedder" promise is two CHANGELOG sentences: v2.4.0 ("An
  application that links its own copy of sparsemap can no longer collide")
  and v2.6.0 ("shipped for embedders, not called by libumem itself").
- No man page, README section, installed header or `pkg-config` entry
  documents them. An embedder would have to copy `sm.h` out of the source
  tree and compile with `-DSPARSEMAP_PREFIX=umem_` to call them.
- Namespacing was introduced to avoid *collision*. That goal is already met
  by not exporting the symbols at all.
- libumem has kept `-version-info 1:0:0` since v2.3.0, even though these 86
  symbols appeared in v2.4.0. The added ABI was never reflected in the
  soname version.

**Options** (the coordinator decides; nothing was changed here):

- **Keep as is.** An undocumented ABI promise to nobody. Every future sparsemap
  bug becomes a libumem exposure question, as this review had to establish.
  The ~55–58 KB of text sits in every process that loads libumem, including
  `LD_PRELOAD` into setuid/root targets (AGENTS.md §7a positions A/B). There
  it is dead but executable code.
- **Hide.** Compile `sm.c` with `-fvisibility=hidden`, which is sufficient
  because sm.h declares no visibility attributes. Alternatively, use a linker
  version script for libumem that exports only `umem_*` minus `umem_sm_*`.
  This keeps the source for a possible future internal user and removes the
  ABI surface. Since the code is unreferenced, `--gc-sections` would then drop
  most of it. It is a visible ABI removal and needs a CHANGELOG line and a
  `-version-info` bump.
- **Drop.** Remove `sm.c`/`sm.h` from `libumem_la_SOURCES` (which
  `libumem_ptcprobe_la_SOURCES` reuses), and delete them along with the
  dead `test/common.[ch]`.
  - YAGNI: no caller in the ~7 weeks since vendoring, and the GC that
    motivated the page-map work is gone.
  - This removes the dependency-review burden entirely, as well as the
    `sm.c` share of the coverage denominator (29% of instrumented lines per
    the 2026-09-06 coverage report).
  - Same ABI-removal consequences as "hide".

**Recommendation: drop.** Failing that, hide. The symbols serve no in-tree
code, no documented API and no known consumer. The one reason given for
shipping them ("for embedders") was never backed by a header, a document or
a test. Hiding keeps a maintenance and review obligation for no user. If an
internal consumer ever appears, re-vendor then, at whatever upstream version
is current and correct.
