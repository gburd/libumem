      43              :  * \section Nuances
      44              :  *
      45              :  * There is a nuance in the behaviour of the umem port compared
      46              :  * with umem on Solaris.
      47              :  *
      48              :  * On Linux umem will not return memory back to the OS until umem fails
      49              :  * to allocate a chunk. On failure, umem_reap() will be called automatically,
      50              :  * to return memory to the OS. If your code is going to be running
      51              :  * for a long time on Linux and mixes calls to different memory allocators
      52              :  * (e.g.: malloc()) and umem, your code will need to call
      53              :  * umem_reap() periodically.
      54              :  *
      55              :  * This doesn't happen on Solaris, because malloc is replaced
      56              :  * with umem calls, meaning that umem_reap() is called automatically.
      57              :  *
      58              :  * \section References
      59              :  *
      60              :  * http://docs.sun.com/app/docs/doc/816-5173/6mbb8advq?a=view
      61              :  *
      62              :  * http://access1.sun.com/techarticles/libumem.html
      63              :  *
      64              :  * \section Overview
      65              :  *
      66              :  * \code
      67              :  * based on usr/src/uts/common/os/kmem.c r1.64 from 2001/12/18
      68              :  *
      69              :  * The slab allocator, as described in the following two papers:
      70              :  *
      71              :  *      Jeff Bonwick,
      72              :  *      The Slab Allocator: An Object-Caching Kernel Memory Allocator.
      73              :  *      Proceedings of the Summer 1994 Usenix Conference.
      74              :  *      Available as /shared/sac/PSARC/1994/028/materials/kmem.pdf.
      75              :  *
      76              :  *      Jeff Bonwick and Jonathan Adams,
      77              :  *      Magazines and vmem: Extending the Slab Allocator to Many CPUs and
      78              :  *      Arbitrary Resources.
      79              :  *      Proceedings of the 2001 Usenix Conference.
      80              :  *      Available as /shared/sac/PSARC/2000/550/materials/vmem.pdf.
      81              :  *
      82              :  * 1. Overview
      83              :  * -----------
      84              :  * umem is very close to kmem in implementation.  There are seven major
      85              :  * areas of divergence:
      86              :  *
      87              :  *      * Initialization
      88              :  *
      89              :  *      * CPU handling
      90              :  *
      91              :  *      * umem_update()
      92              :  *
      93              :  *      * KM_SLEEP v.s. UMEM_NOFAIL
      94              :  *
      95              :  *  * lock ordering
      96              :  *
      97              :  *      * changing UMEM_MAXBUF
      98              :  *
      99              :  *      * Per-thread caching for malloc/free
     100              :  *
     101              :  * 2. Initialization
     102              :  * -----------------
     103              :  * kmem is initialized early on in boot, and knows that no one will call
     104              :  * into it before it is ready.  umem does not have these luxuries. Instead,
     105              :  * initialization is divided into two phases:
     106              :  *
     107              :  *      * library initialization, and
     108              :  *
     109              :  *      * first use
     110              :  *
     111              :  * umem's full initialization happens at the time of the first allocation
     112              :  * request (via malloc() and friends, umem_alloc(), or umem_zalloc()),
     113              :  * or the first call to umem_cache_create().
     114              :  *
     115              :  * umem_free(), and umem_cache_alloc() do not require special handling,
     116              :  * since the only way to get valid arguments for them is to successfully
     117              :  * call a function from the first group.
     118              :  *
     119              :  * 2.1. Library Initialization: umem_startup()
     120              :  * -------------------------------------------
     121              :  * umem_startup() is libumem.so's .init section.  It calls pthread_atfork()
     122              :  * to install the handlers necessary for umem's Fork1-Safety.  Because of
     123              :  * race condition issues, all other pre-umem_init() initialization is done
     124              :  * statically (i.e. by the dynamic linker).
     125              :  *
     126              :  * For standalone use, umem_startup() returns everything to its initial
     127              :  * state.
     128              :  *
     129              :  * 2.2. First use: umem_init()
     130              :  * ------------------------------
     131              :  * The first time any memory allocation function is used, we have to
     132              :  * create the backing caches and vmem arenas which are needed for it.
     133              :  * umem_init() is the central point for that task.  When it completes,
     134              :  * umem_ready is either UMEM_READY (all set) or UMEM_READY_INIT_FAILED (unable
     135              :  * to initialize, probably due to lack of memory).
     136              :  *
     137              :  * There are four different paths from which umem_init() is called:
     138              :  *
     139              :  *      * from umem_alloc() or umem_zalloc(), with 0 < size < UMEM_MAXBUF,
     140              :  *
     141              :  *      * from umem_alloc() or umem_zalloc(), with size > UMEM_MAXBUF,
     142              :  *
     143              :  *      * from umem_cache_create(), and
     144              :  *
     145              :  *      * from memalign(), with align > UMEM_ALIGN.
     146              :  *
     147              :  * The last three just check if umem is initialized, and call umem_init()
     148              :  * if it is not.  For performance reasons, the first case is more complicated.
     149              :  *
     150              :  * 2.2.1. umem_alloc()/umem_zalloc(), with 0 < size < UMEM_MAXBUF
     151              :  * -----------------------------------------------------------------
     152              :  * In this case, umem_cache_alloc(&umem_null_cache, ...) is called.
     153              :  * There is special case code in which causes any allocation on
     154              :  * &umem_null_cache to fail by returning (NULL), regardless of the
     155              :  * flags argument.
     156              :  *
     157              :  * So umem_cache_alloc() returns NULL, and umem_alloc()/umem_zalloc() call
     158              :  * umem_alloc_retry().  umem_alloc_retry() sees that the allocation
     159              :  * was agains &umem_null_cache, and calls umem_init().
     160              :  *
     161              :  * If initialization is successful, umem_alloc_retry() returns 1, which
     162              :  * causes umem_alloc()/umem_zalloc() to start over, which causes it to load
     163              :  * the (now valid) cache pointer from umem_alloc_table.
     164              :  *
     165              :  * 2.2.2. Dealing with race conditions
     166              :  * -----------------------------------
     167              :  * There are a couple race conditions resulting from the initialization
     168              :  * code that we have to guard against:
     169              :  *
     170              :  *      * In umem_cache_create(), there is a special UMC_INTERNAL cflag
     171              :  *      that is passed for caches created during initialization.  It
     172              :  *      is illegal for a user to try to create a UMC_INTERNAL cache.
     173              :  *      This allows initialization to proceed, but any other
     174              :  *      umem_cache_create()s will block by calling umem_init().
     175              :  *
     176              :  *      * Since umem_null_cache has a 1-element cache_cpu, it's cache_cpu_mask
     177              :  *      is always zero.  umem_cache_alloc uses cp->cache_cpu_mask to
     178              :  *      mask the cpu number.  This prevents a race between grabbing a
     179              :  *      cache pointer out of umem_alloc_table and growing the cpu array.
     180              :  *
     181              :  *
     182              :  * 3. CPU handling
     183              :  * ---------------
     184              :  * kmem uses the CPU's sequence number to determine which "cpu cache" to
     185              :  * use for an allocation.  Currently, there is no way to get the sequence
     186              :  * number in userspace.
     187              :  *
     188              :  * umem keeps track of cpu information in umem_cpus, an array of umem_max_ncpus
     189              :  * umem_cpu_t structures.  CURCPU() is a a "hint" function, which we then mask
     190              :  * with either umem_cpu_mask or cp->cache_cpu_mask to find the actual "cpu" id.
     191              :  * The mechanics of this is all in the CPU(mask) macro.
     192              :  *
     193              :  * Currently, umem uses _lwp_self() as its hint.
     194              :  *
     195              :  *
     196              :  * 4. The update thread
     197              :  * --------------------
     198              :  * kmem uses a task queue, kmem_taskq, to do periodic maintenance on
     199              :  * every kmem cache.  vmem has a periodic timeout for hash table resizing.
     200              :  * The kmem_taskq also provides a separate context for kmem_cache_reap()'s
     201              :  * to be done in, avoiding issues of the context of kmem_reap() callers.
     202              :  *
     203              :  * Instead, umem has the concept of "updates", which are asynchronous requests
     204              :  * for work attached to single caches.  All caches with pending work are
     205              :  * on a doubly linked list rooted at the umem_null_cache.  All update state
     206              :  * is protected by the umem_update_lock mutex, and the umem_update_cv is used
     207              :  * for notification between threads.
     208              :  *
     209              :  * 4.1. Cache states with regards to updates
     210              :  * -----------------------------------------
     211              :  * A given cache is in one of three states:
     212              :  *
     213              :  * Inactive             cache_uflags is zero, cache_u{next,prev} are NULL
     214              :  *
     215              :  * Work Requested       cache_uflags is non-zero (but UMU_ACTIVE is not set),
     216              :  *                      cache_u{next,prev} link the cache onto the global
     217              :  *                      update list
     218              :  *
     219              :  * Active               cache_uflags has UMU_ACTIVE set, cache_u{next,prev}
     220              :  *                      are NULL, and either umem_update_thr or
     221              :  *                      umem_st_update_thr are actively doing work on the
     222              :  *                      cache.
     223              :  *
     224              :  * An update can be added to any cache in any state -- if the cache is
     225              :  * Inactive, it transitions to being Work Requested.  If the cache is
     226              :  * Active, the worker will notice the new update and act on it before
     227              :  * transitioning the cache to the Inactive state.
     228              :  *
     229              :  * If a cache is in the Active state, UMU_NOTIFY can be set, which asks
     230              :  * the worker to broadcast the umem_update_cv when it has finished.
     231              :  *
     232              :  * 4.2. Update interface
     233              :  * ---------------------
     234              :  * umem_add_update() adds an update to a particular cache.
     235              :  * umem_updateall() adds an update to all caches.
     236              :  * umem_remove_updates() returns a cache to the Inactive state.
     237              :  *
     238              :  * umem_process_updates() process all caches in the Work Requested state.
     239              :  *
     240              :  * 4.3. Reaping
     241              :  * ------------
     242              :  * When umem_reap() is called (at the time of heap growth), it schedule
     243              :  * UMU_REAP updates on every cache.  It then checks to see if the update
     244              :  * thread exists (umem_update_thr != 0).  If it is, it broadcasts
     245              :  * the umem_update_cv to wake the update thread up, and returns.
     246              :  *
     247              :  * If the update thread does not exist (umem_update_thr == 0), and the
     248              :  * program currently has multiple threads, umem_reap() attempts to create
     249              :  * a new update thread.
     250              :  *
     251              :  * If the process is not multithreaded, or the creation fails, umem_reap()
     252              :  * calls umem_st_update() to do an inline update.
     253              :  *
     254              :  * 4.4. The update thread
     255              :  * ----------------------
     256              :  * The update thread spends most of its time in cond_timedwait() on the
     257              :  * umem_update_cv.  It wakes up under two conditions:
     258              :  *
     259              :  *      * The timedwait times out, in which case it needs to run a global
     260              :  *      update, or
     261              :  *
     262              :  *      * someone cond_broadcast(3THR)s the umem_update_cv, in which case
     263              :  *      it needs to check if there are any caches in the Work Requested
     264              :  *      state.
     265              :  *
     266              :  * When it is time for another global update, umem calls umem_cache_update()
     267              :  * on every cache, then calls vmem_update(), which tunes the vmem structures.
     268              :  * umem_cache_update() can request further work using umem_add_update().
     269              :  *
     270              :  * After any work from the global update completes, the update timer is
     271              :  * reset to umem_reap_interval seconds in the future.  This makes the
     272              :  * updates self-throttling.
     273              :  *
     274              :  * Reaps are similarly self-throttling.  After a UMU_REAP update has
     275              :  * been scheduled on all caches, umem_reap() sets a flag and wakes up the
     276              :  * update thread.  The update thread notices the flag, and resets the
     277              :  * reap state.
     278              :  *
     279              :  * 4.5. Inline updates
     280              :  * -------------------
     281              :  * If the update thread is not running, umem_st_update() is used instead.  It
     282              :  * immediately does a global update (as above), then calls
     283              :  * umem_process_updates() to process both the reaps that umem_reap() added and
     284              :  * any work generated by the global update.  Afterwards, it resets the reap
     285              :  * state.
     286              :  *
     287              :  * While the umem_st_update() is running, umem_st_update_thr holds the thread
     288              :  * id of the thread performing the update.
     289              :  *
     290              :  * 4.6. Updates and fork1()
     291              :  * ------------------------
     292              :  * umem has fork1() pre- and post-handlers which lock up (and release) every
     293              :  * mutex in every cache.  They also lock up the umem_update_lock.  Since
     294              :  * fork1() only copies over a single lwp, other threads (including the update
     295              :  * thread) could have been actively using a cache in the parent.  This
     296              :  * can lead to inconsistencies in the child process.
     297              :  *
     298              :  * Because we locked all of the mutexes, the only possible inconsistancies are:
     299              :  *
     300              :  *      * a umem_cache_alloc() could leak its buffer.
     301              :  *
     302              :  *      * a caller of umem_depot_alloc() could leak a magazine, and all the
     303              :  *      buffers contained in it.
     304              :  *
     305              :  *      * a cache could be in the Active update state.  In the child, there
     306              :  *      would be no thread actually working on it.
     307              :  *
     308              :  *      * a umem_hash_rescale() could leak the new hash table.
     309              :  *
     310              :  *      * a umem_magazine_resize() could be in progress.
     311              :  *
     312              :  *      * a umem_reap() could be in progress.
     313              :  *
     314              :  * The memory leaks we can't do anything about.  umem_release_child() resets
     315              :  * the update state, moves any caches in the Active state to the Work Requested
     316              :  * state.  This might cause some updates to be re-run, but UMU_REAP and
     317              :  * UMU_HASH_RESCALE are effectively idempotent, and the worst that can
     318              :  * happen from umem_magazine_resize() is resizing the magazine twice in close
     319              :  * succession.
     320              :  *
     321              :  * Much of the cleanup in umem_release_child() is skipped if
     322              :  * umem_st_update_thr == thr_self().  This is so that applications which call
     323              :  * fork1() from a cache callback does not break.  Needless to say, any such
     324              :  * application is tremendously broken.
     325              :  *
     326              :  *
     327              :  * 5. KM_SLEEP v.s. UMEM_NOFAIL
     328              :  * ----------------------------
     329              :  * Allocations against kmem and vmem have two basic modes:  SLEEP and
     330              :  * NOSLEEP.  A sleeping allocation is will go to sleep (waiting for
     331              :  * more memory) instead of failing (returning NULL).
     332              :  *
     333              :  * SLEEP allocations presume an extremely multithreaded model, with
     334              :  * a lot of allocation and deallocation activity.  umem cannot presume
     335              :  * that its clients have any particular type of behavior.  Instead,
     336              :  * it provides two types of allocations:
     337              :  *
     338              :  *      * UMEM_DEFAULT, equivalent to KM_NOSLEEP (i.e. return NULL on
     339              :  *      failure)
     340              :  *
     341              :  *      * UMEM_NOFAIL, which, on failure, calls an optional callback
     342              :  *      (registered with umem_nofail_callback()).
     343              :  *
     344              :  * The callback is invoked with no locks held, and can do an arbitrary
     345              :  * amount of work.  It then has a choice between:
     346              :  *
     347              :  *      * Returning UMEM_CALLBACK_RETRY, which will cause the allocation
     348              :  *      to be restarted.
     349              :  *
     350              :  *      * Returning UMEM_CALLBACK_EXIT(status), which will cause exit(2)
     351              :  *      to be invoked with status.  If multiple threads attempt to do
     352              :  *      this simultaneously, only one will call exit(2).
     353              :  *
     354              :  *      * Doing some kind of non-local exit (thr_exit(3thr), longjmp(3C),
     355              :  *      etc.)
     356              :  *
     357              :  * The default callback returns UMEM_CALLBACK_EXIT(255).
     358              :  *
     359              :  * To have these callbacks without risk of state corruption (in the case of
     360              :  * a non-local exit), we have to ensure that the callbacks get invoked
     361              :  * close to the original allocation, with no inconsistent state or held
     362              :  * locks.  The following steps are taken:
     363              :  *
     364              :  *      * All invocations of vmem are VM_NOSLEEP.
     365              :  *
     366              :  *      * All constructor callbacks (which can themselves to allocations)
     367              :  *      are passed UMEM_DEFAULT as their required allocation argument.  This
     368              :  *      way, the constructor will fail, allowing the highest-level allocation
     369              :  *      invoke the nofail callback.
     370              :  *
     371              :  *      If a constructor callback _does_ do a UMEM_NOFAIL allocation, and
     372              :  *      the nofail callback does a non-local exit, we will leak the
     373              :  *      partially-constructed buffer.
     374              :  *
     375              :  *
     376              :  * 6. Lock Ordering
     377              :  * ----------------
     378              :  * umem has a few more locks than kmem does, mostly in the update path.  The
     379              :  * overall lock ordering (earlier locks must be acquired first) is:
     380              :  *
     381              :  *      umem_init_lock
     382              :  *
     383              :  *      vmem_list_lock
     384              :  *      vmem_nosleep_lock.vmpl_mutex
     385              :  *      vmem_t's:
     386              :  *              vm_lock
     387              :  *      sbrk_lock
     388              :  *
     389              :  *      umem_cache_lock
     390              :  *      umem_update_lock
     391              :  *      umem_flags_lock
     392              :  *      umem_cache_t's:
     393              :  *              cache_cpu[*].cc_lock
     394              :  *              cache_depot_lock
     395              :  *              cache_lock
     396              :  *      umem_log_header_t's:
     397              :  *              lh_cpu[*].clh_lock
     398              :  *              lh_lock
     399              :  *
     400              :  * \endcode
     401              :  *
     402              :  * 7. Changing UMEM_MAXBUF
     403              :  * -----------------------
     404              :  *
     405              :  * When changing UMEM_MAXBUF extra care has to be taken. It is not sufficient to
     406              :  * simply increase this number. First, one must update the umem_alloc_table to
     407              :  * have the appropriate number of entires based upon the new size. If this is
     408              :  * not done, this will lead to libumem blowing an assertion.
     409              :  *
     410              :  * The second place to update, which is not required, is the umem_alloc_sizes.
     411              :  * These determine the default cache sizes that we're going to support.
     412              :  *
     413              :  * 8. Per-thread caching for malloc/free
     414              :  * -------------------------------------
     415              :  *
     416              :  * "Time is an illusion. Lunchtime doubly so." -- Douglas Adams
     417              :  *
     418              :  * Time may be an illusion, but CPU cycles aren't.  While libumem is designed
     419              :  * to be a highly scalable allocator, that scalability comes with a fixed cycle
     420              :  * penalty even in the absence of contention: libumem must acquire (and release
     421              :  * a per-CPU lock for each allocation.  When contention is low and malloc(3C)
     422              :  * frequency is high, this overhead can dominate execution time.  To alleviate
     423              :  * this, we allow for per-thread caching, a lock-free means of caching recent
     424              :  * deallocations on a per-thread basis for use in satisfying subsequent calls
     425              :  *
     426              :  * In addition to improving performance, we also want to:
     427              :  *      * Minimize fragmentation
     428              :  *      * Not add additional memory overhead (no larger malloc tags)
     429              :  *
     430              :  * In the ulwp_t of each thread there is a private data structure called a
     431              :  * umem_t that looks like:
     432              :  *
     433              :  * typedef struct {
     434              :  *      size_t  tm_size;
     435              :  *      void    *tm_roots[NTMEMBASE];  (Currently 16)
     436              :  * } tmem_t;
     437              :  *
     438              :  * Each of the roots is treated as the head of a linked list. Each entry in the
     439              :  * list can be thought of as a void ** which points to the next entry, until one
     440              :  * of them points to NULL. If the head points to NULL, the list is empty.
     441              :  *
     442              :  * Each head corresponds to a umem_cache. Currently there is a linear mapping
     443              :  * where the first root corresponds to the first cache, second root to the
     444              :  * second cache, etc. This works because every allocation that malloc makes to
     445              :  * umem_alloc that can be satisified by a umem_cache will actually return a
     446              :  * number of bytes equal to the size of that cache. Because of this property and
     447              :  * a one to one mapping between caches and roots we can guarantee that every
     448              :  * entry in a given root's list will be able to satisfy the same requests as the
     449              :  * corresponding cache.
     450              :  *
     451              :  * The choice of sixteen roots is based on where we believe we get the biggest
     452              :  * bang for our buck. The per-thread caches will cache up to 256 byte and 448
     453              :  * byte allocations on ILP32 and LP64 respectively. Generally applications plan
     454              :  * more carefully how they do larger allocations than smaller ones. Therefore
     455              :  * sixteen roots is a reasonable compromise between the amount of additional
     456              :  * overhead per thread, and the likelihood of a program to benefit from it.
     457              :  *
     458              :  * The maximum amount of memory that can be cached in each thread is determined
     459              :  * by the perthread_cache UMEM_OPTION. It corresponds to the umem_ptc_size
     460              :  * value. The default value for this is currently 1 MB. Once umem_init() has
     461              :  * finished this cannot be directly tuned without directly modifying the
     462              :  * instruction text. If, upon calling free(3C), the amount cached would exceed
     463              :  * this maximum, we instead actually return the buffer to the umem_cache instead
     464              :  * of holding onto it in the thread.
     465              :  *
     466              :  * When a thread calls malloc(3C) it first determines which umem_cache it
     467              :  * would be serviced by. If the allocation is not covered by ptcumem it goes to
     468              :  * the normal malloc instead.  Next, it checks if the tmem_root's list is empty
     469              :  * or not. If it is empty, we instead go and allocate the memory from
     470              :  * umem_alloc. If it is not empty, we remove the head of the list, set the
     471              :  * appropriate malloc tags, and return that buffer.
     472              :  *
     473              :  * When a thread calls free(3C) it first looks at the malloc tag and if it is
     474              :  * invalid or the allocation exceeds the largest cache in ptcumem and sends it
     475              :  * off to the original free() to handle and clean up appropriately. Next, it
     476              :  * checks if the allocation size is covered by one of the per-thread roots and
     477              :  * if it isn't, it passes it off to the original free() to be released. Finally,
     478              :  * before it inserts this buffer as the head, it checks if adding this buffer
     479              :  * would put the thread over its maximum cache size. If it would, it frees the
     480              :  * buffer back to the umem_cache. Otherwise it increments the threads total
     481              :  * cached amount and makes the buffer the new head of the appropriate tm_root.
     482              :  *
     483              :  * When a thread exits, all of the buffers that it has in its per-thread cache
     484              :  * will be passed to umem_free() and returned to the appropriate umem_cache.
     485              :  *
     486              :  * 8.1 Handling addition and removal of umem_caches
     487              :  * ------------------------------------------------
     488              :  *
     489              :  * The set of umem_caches that are used to back calls to umem_alloc() and
     490              :  * ultimately malloc() are determined at program execution time. The default set
     491              :  * of caches is defined below in umem_alloc_sizes[]. Various umem_options exist
     492              :  * that modify the set of caches: size_add, size_clear, and size_remove. Because
     493              :  * the set of caches can only be determined once umem_init() has been called and
     494              :  * we have the additional goals of minimizing additional fragmentation and
     495              :  * metadata space overhead in the malloc tags, this forces our hand to go down a
     496              :  * slightly different path: the one tread by fasttrap and trapstat.
     497              :  *
     498              :  * During umem_init we're going to dynamically construct a new version of
     499              :  * malloc(3C) and free(3C) that utilizes the known cache sizes and then ensure
     500              :  * that ptcmalloc and ptcfree replace malloc and free as entries in the plt. If
     501              :  * ptcmalloc and ptcfree cannot handle a request, they simply jump to the
     502              :  * original libumem implementations.
     503              :  *
     504              :  * After creating all of the umem_caches, but before making them visible,
     505              :  * umem_cache_init checks that umem_genasm_supported is non-zero. This value is
     506              :  * set by each architecture in $ARCH/umem_genasm.c to indicate whether or not
     507              :  * they support this. If the value is zero, then this process is skipped.
     508              :  * Similarly, if the cache size has been tuned to zero by UMEM_OPTIONS, then
     509              :  * this is also skipped.
     510              :  *
     511              :  * In umem_genasm.c, each architecture's implementation implements a single
     512              :  * function called umem_genasm() that is responsible for generating the
     513              :  * appropriate versions of ptcmalloc() and ptcfree(), placing them in the
     514              :  * appropriate memory location, and finally doing the switch from malloc() and
     515              :  * free() to ptcmalloc() and ptcfree().  Once the change has been made, there is
     516              :  * no way to switch back, short of restarting the program or modifying program
     517              :  * text with mdb.
     518              :  *
     519              :  * 8.2 Modifying the Procedure Linkage Table (PLT)
     520              :  * -----------------------------------------------
     521              :  *
     522              :  * The last piece of this puzzle is how we actually jam ptcmalloc() into the
     523              :  * PLT.  To handle this, we have defined two functions, _malloc and _free and
     524              :  * used a special mapfile directive to place them into the a readable,
     525              :  * writeable, and executable segment.  Next we use a standard #pragma weak for
     526              :  * malloc and free and direct them to those symbols. By default, those symbols
     527              :  * have text defined as nops for our generated functions and when they're
     528              :  * invoked, they jump to the default malloc and free functions.
     529              :  *
     530              :  * When umem_genasm() is called, it goes through and generates new malloc() and
     531              :  * free() functions in the text provided for by _malloc and _free just after the
     532              :  * jump. Once both have been successfully generated, umem_genasm() nops over the
     533              :  * original jump so that we now call into the genasm versions of these
     534              :  * functions.
     535              :  *
     536              :  * 8.3 umem_genasm()
     537              :  * -----------------
     538              :  *
     539              :  * umem_genasm() is currently implemented for i386 and amd64. This section
     540              :  * describes the theory behind the construction. For specific byte code to
     541              :  * assembly instructions and niceish C and asm versions of ptcmalloc and
     542              :  * ptcfree, see the individual umem_genasm.c files. The layout consists of the
     543              :  * following sections:
     544              :  *
     545              :  *      o. function-specfic prologue
     546              :  *      o. function-generic cache-selecting elements
     547              :  *      o. function-specific epilogue
     548              :  *
     549              :  * There are three different generic cache elements that exist:
     550              :  *
     551              :  *      o. the last or only cache
     552              :  *      o. the intermediary caches if more than two
     553              :  *      o. the first one if more than one cache
     554              :  *
     555              :  * The malloc and free prologues and epilogues mimic the necessary portions of
     556              :  * libumem's malloc and free. This includes things like checking for size
     557              :  * overflow, setting and verifying the malloc tags.
     558              :  *
     559              :  * It is an important constraint that these functions do not make use of the
     560              :  * call instruction. The only jmp outside of the individual functions is to the
     561              :  * original libumem malloc and free respectively. Because doing things like
     562              :  * setting errno or raising an internal umem error on improper malloc tags would
     563              :  * require using calls into the PLT, whenever we encounter one of those cases we
     564              :  * just jump to the original malloc and free functions reusing the same stack
     565              :  * frame.
     566              :  *
     567              :  * Each of the above sections, the three caches, and the malloc and free
     568              :  * prologue and epilogue are implemented as blocks of machine code with the
     569              :  * corresponding assembly in comments. There are known offsets into each block
     570              :  * that corresponds to locations of data and addresses that we only know at run
     571              :  * time. These blocks are copied as necessary and the blanks filled in
     572              :  * appropriately.
     573              :  *
     574              :  * As mentioned in section 8.2, the trampoline library uses specifically named
     575              :  * variables to communicate the buffers and size to use. These variables are:
     576              :  *
     577              :  *      o. umem_genasm_mptr: The buffer for ptcmalloc
     578              :  *      o. umem_genasm_msize: The size in bytes of the above buffer
     579              :  *      o. umem_genasm_fptr: The buffer for ptcfree
     580              :  *      o. umem_genasm_fsize: The size in bytes of the above buffer
     581              :  *
     582              :  * Finally, to enable the generated assembly we need to remove the previous jump
     583              :  * to the actual malloc that exists at the start of these buffers. On x86, this
     584              :  * is a five byte region. We could zero out the jump offset to be a jmp +0, but
     585              :  * using nops can be faster. We specifically use a single five byte nop on x86
     586              :  * as it is faster. When porting ptcumem to other architectures, the various
     587              :  * opcode changes and options should be analyzed.
     588              :  *
     589              :  * 8.4 Interface with libc.so
     590              :  * --------------------------
     591              :  *
     592              :  * The tmem_t structure as described in the beginning of section 8, is part of a
     593              :  * private interface with libc. There are three functions that exist to cover
     594              :  * this. They are not documented in man pages or header files. They are in the
     595              :  * SUNWprivate part of libc's mapfile.
     596              :  *
     597              :  *      o. _tmem_get_base(void)
     598              :  *
     599              :  *      Returns the offset from the ulwp_t (curthread) to the tmem_t structure.
     600              :  *      This is a constant for all threads and is effectively a way to to do
     601              :  *      ::offsetof ulwp_t ul_tmem without having to know the specifics of the
     602              :  *      structure outside of libc.
     603              :  *
     604              :  *      o. _tmem_get_nentries(void)
     605              :  *
     606              :  *      Returns the number of roots that exist in the tmem_t. This is one part
     607              :  *      of the cap on the number of umem_caches that we can back with tmem.
     608              :  *
     609              :  *      o. _tmem_set_cleanup(void (*)(void *, int))
     610              :  *
     611              :  *      This sets a clean up handler that gets called back when a thread exits.
     612              :  *      There is one call per buffer, the void * is a pointer to the buffer on
     613              :  *      the list, the int is the index into the roots array for this buffer.
